## 3. Key Concepts & Formal Definitions

| Concept / Term | Formal Definition & Operational Meaning | Contextual Constraints / Properties |
| :--- | :--- | :--- |
| **Functional Requirements (FRs)** | Decomposed specifications derived by the internal engineering team from raw user/client requirements defining precise system operations. | Purely internal development artifacts; abstract client requirements do not dictate direct engineering modularity. |
| **Modularization** | The architectural practice of partitioning an embedded application into independently implementable and testable functional units. | Each subsystem must allow decoupled verification prior to full system integration. |
| **System Architecture** | Structural description capturing data flow graphs (DFG) and control flow graphs (CFG) across hardware and software blocks. | Distinguished from high-level block diagrams; architecture explicitly encodes operational execution paths, function sequences, and data transitions. |
| **Hardware-Software Co-Design** | Parallel, concurrent design and synthesis of custom software stacks and underlying hardware circuits targeted for a dedicated system. | Distinguishes embedded engineering from generic computing (e.g., standard PC/OS deployment), where software and hardware are developed in isolation. |
| **Compatibility** | The structural and electrical agreement between integrated modules permitting mutual data exchange. | Requires identical bus logic, bit timings, framing configurations, and matching protocol specifications. |
| **Cohesivity** | The operational sufficiency of signal amplitude, signal-to-noise ratio, or receiver sensitivity across an interconnect. | Dictated by operational distance, line capacitance, and physical medium limitations (e.g., I2C on-board vs. UART/SPI over meters). |
| **Interrupt** | An asynchronous or synchronous electrical signal generated by an internal or external peripheral requesting immediate CPU servicing. | Peripherals merely assert request signals; CPU logic retains ultimate arbitration authority to service, defer, or ignore the signal. |
| **Interrupt Service Routine (ISR)** | Dedicated executable subroutine mapped to an interrupt vector designed to service an asserted peripheral condition. | Must remain minimal and computationally compact to minimize context switching overhead and latency. |
| **Context Switching Time (CST)** | The aggregate latency incurred by saving the currently executing process state to stack memory and subsequent state restoration upon ISR return. | Unavoidable execution overhead; high frequency of context switches degrades net computational throughput. |
| **Vectored Interrupt** | An interrupt architecture wherein the hardware or memory architecture binds a pre-assigned, fixed memory address to the ISR. | Allows fast direct branch dispatch through an Interrupt Vector Table (IVT) without programmatic polling of interrupt identity. |
| **Non-Vectored Interrupt** | An interrupt scheme where the starting address of the corresponding service routine is not hard-wired and must be supplied dynamically. | Requires peripheral-supplied vector identification or software interrogation to compute the routine target. |
| **Maskable Interrupt** | An interrupt whose detection logic can be enabled or suppressed dynamically by manipulating internal control registers. | Masking does not halt peripheral flag assertion; it instructs the interrupt controller to ignore asserted flags. |
| **Non-Maskable Interrupt (NMI)** | An ultra-high-priority interrupt line that bypasses programmatic masking registers and forces CPU dispatch (e.g., system Reset, memory bus faults). | Reserved for mission-critical operations, fatal hardware traps, and memory access integrity violations. |
| **Watchdog Timer (WDT)** | An autonomous countdown timer circuit designed to reset the CPU to baseline execution if software fails to clear it within a stipulated time window. | Mitigates system deadlocks, software infinite loops, or halted states (e.g., uncompleted transactions at an ATM kiosk). |
| **Brownout Timer / Circuit** | Voltage monitoring logic that forces safe system reset or low-power state preservation when supply rails drop beneath an operational threshold. | Grants brief millisecond windows to flush kernel structures and safely park storage before power vanishes. |
| **Sporadic Task** | A workload sequence that occurs intermittently or aperiodically, but only within well-defined, periodic temporal envelopes. | Periodically aperiodic; workload presence is bounded to specific seasonal or daily operation windows. |

## 4. Detailed Structured Technical Lecture Notes

### I. Embedded System Design Lifecycle & Co-Design Paradigms

#### Overview & Theoretical Foundation
The embedded system development lifecycle begins with requirements gathering from end clients or users. Unlike general-purpose computing platforms—such as standard desktop computers or laptops where operating systems and motherboards are developed through decoupled, independent supply chains—embedded system engineering demands hardware-software co-design. Under co-design, physical circuits and low-level firmware progress parallelly to converge upon a specialized prototype satisfying strict real-time and physical constraints.

```
|  - Feasibility: Technological Boundary Validation           |
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|              Functional Requirements (FRs) List             |

+-------------------------------------------------------------+
```

#### Mechanics & Operational Invariants
1. **Requirement Phase & Feasibility Analysis:**
   * **Time Audits:** Evaluating total implementation schedules (*time-to-develop*) aligned against commercial delivery windows (*time-to-market*).
   * **Resource Audits:** Verification of personnel, physical testing equipment, target IC availability, compiler toolchains, and proprietary Intellectual Property (IP) blocks.
   * **Technological Bound Assessment:** Validating whether requested client functionality exceeds modern silicon or algorithmic thresholds. If unsupported, requirements must be altered prior to design sign-off.
2. **Modularization Mechanics:**
   * High-level functional specifications are translated into concrete functional requirements (FRs).
   * The engineering team decomposes the design into discrete sub-components that can be independently developed, debugged, and verified prior to bus aggregation.
3. **Architectural Modeling vs. Block Diagrams:**
   * High-level block diagrams identify merely the physical boundaries of discrete microcontrollers, communication ICs, and auxiliary sensors.
   * Formal system architectures construct rigorous Data Flow Graphs (DFG) and Control Flow Graphs (CFG). The architecture explicitly governs data serialization, payload interchange timing, invocation order of function trees, and conditional state dependencies.
4. **Prototyping Invariants:**
   * The prototype represents a minimal functional model focused exclusively on validating the functional requirement checklist.
   * Prototypes typically omit auxiliary production hardening, including transient suppression circuitry, industrial casing, reverse polarity protection, and extensive defensive software wrappers.

#### Component Selection Matrix: On-Chip vs. Off-Chip Peripherals
| Selection Category | Performance Advantages | Practical Constraints & Drawbacks |
| :--- | :--- | :--- |
| **On-Chip Peripherals** | Superior execution speed, lowest parasitic bus latency, minimal power draw, tight die integration, and precise internal timing synchronization. | Silicon inflexibility; peripheral resources cannot be dynamically swapped, updated, or expanded post-fabrication. |
| **Off-Chip Peripherals** | High architectural modularity; individual sub-components can be upgraded, replaced, or interchanged throughout the system lifecycle. | Increased PCB footprint, higher power dissipation, reduced operational frequency, and susceptibility to trace noise and timing skew. |

### II. Multi-Level Testing & Interfacing Verification

#### Overview & Theoretical Foundation
Testing in embedded systems verifies structural integrity, software logic, and electrical margins. Due to the coupling between software and physical signals, embedded verification bifurcates into unit/component verification, subsystem integration, and multi-node network verification. System integration tests whether independent modules maintain structural compatibility and cohesive signal levels across target communication channels.

#### Mechanics & Operational Invariants
1. **Component / Unit Verification:**
   * **Software Modules:** Subjected to unit testing to ensure deterministic code coverage, absence of arithmetic overflow, and compliance with FR functional specifications.
   * **Hardware Circuits:** Evaluated for electrical drive limits and operating endurance. Microcontroller GPIO lines possess severely limited current sourcing and sinking capacities (sufficient only to illuminate minimal low-current LEDs). Inductive loads, high-load relays, and electric motors mandate dedicated hardware driver circuits (e.g., MOSFET switches, H-bridges) to translate logic-level signals into required actuation currents.
   * **Environmental Endurance Testing:** Hardware validation varies by deployment envelope:
     * *Consumer Electronics:* Nominal mechanical shock and standard electrical fluctuation tests.
     * *Automotive Subsystems:* High-amplitude mechanical vibration stress and thermal cycling resistance.
     * *Nuclear / Industrial Power Systems:* High-energy ionizing radiation hardening and electromagnetic interference (EMI) resilience.
2. **Subsystem Integration Mechanics:**
   * Once isolated components pass unit audits, they are integrated across unified communication buses where they encounter cross-cutting compatibility and cohesivity demands.

#### Bus Interfacing: Operational Distance vs. Protocol Selection
| Protocol / Interconnect | Operational Distance Domain | Physical Mechanics & Channel Constraints |
| :--- | :--- | :--- |
| **$\text{I}^2\text{C}$ (Inter-Integrated Circuit)** | Inches (Intra-board domain) | Constrained by bus pull-up resistances and cumulative PCB trace capacitance. Strictly optimized for local, on-board chip communication. |
| **SPI / UART** | 1 meter to 5 meters | Suited for short-range off-board wiring harnesses or high-speed inter-board interfaces. Dedicated UART lines frequently serve as host debug channels to development PCs. |
| **Ethernet / Industrial LAN** | $>5\text{ m}$ to $10\text{ m}+$ | Employs differential signaling and high-layer networking topologies to overcome transmission loss and high-noise industrial environments. |

#### Compatibility vs. Cohesivity Metrics
| Metric | Verification Target | Failure Manifestations & Operational Meaning |
| :--- | :--- | :--- |
| **Compatibility** | Protocol, timing, and formatting parity between sender and receiver. | Frame synchronization failure, mismatching baud rates, inverted logic polarities, or unaligned packet structures. |
| **Cohesivity** | Physical transmission energy, signal-to-noise ratio, and receiver input sensitivity. | The communicating nodes are architecturally compatible, but path attenuation, line resistance, or wireless range limits signal recognition at the receiver. |

### III. System Servicing Topologies: Polling vs. Interrupts

#### Overview & Theoretical Foundation
Microcontrollers communicate with operational peripherals through two core regimes: synchronous continuous polling or asynchronous interrupt-driven servicing. While polling operates sequentially by locking the central core into a continuous read cycle, interrupt systems execute asynchronously. Interrupts allow the CPU to execute background tasks continuously until an external or internal hardware event triggers an asynchronous execution branch.

#### Mechanics & Operational Invariants
1. **Polling Operational Execution:**
   * CPU queries Device 1 status register in an explicit programmatic loop.
   * Processing stalls until Device 1 finishes its operation and updates its status register.
   * CPU services Device 1, subsequently shifts execution to Device 2, entering a wait loop until Device 2 completes, and repeats cyclically.
2. **Interrupt Operational Execution:**
   * The peripheral device detects an internal or physical event (e.g., buffer full, timer overflow) and asserts an Interrupt Request ($\text{IRQ}$) line.
   * The CPU or dedicated Interrupt Controller logs the event bit within an internal **Pending Register**.
   * When eligible, the CPU issues an Interrupt Acknowledge ($\text{IACK}$) signal to the peripheral, suspends the executing program, transitions control to the routine vector, clears the flag, and executes the ISR.

```
       POLLING MECHANISM                             INTERRUPT MECHANISM

    +-----------------------+                    +-------------------------+
    |   CPU Core Execution  |                    | Main Background Process |
    +-----------------------+                    +-------------------------+
                |                                             |
                v                                             |  <-- Peripheral 
     [ Check Device 1 Busy ]                                  |      asserts IRQ
         |             |                                      v
     (No)|             |(Yes)                    +-------------------------+
         |      [ Service Dev 1 ]                | Context Save: Push PC,  |
         v             |                         | CPSR/Status, & GPRs     |
     [ Check Device 2 Busy ]                     +-------------------------+
         |             |                                      |
     (No)|             |(Yes)                                 v
         |      [ Service Dev 2 ]                +-------------------------+
         v             |                         | Execute Associated ISR  |
     [ Check Device 3 Busy ]                     +-------------------------+
         |             |                                      |
     (No)|             |(Yes)                                 v
         |      [ Service Dev 3 ]                +-------------------------+

         | (Repeats in Loop)                     | State & Resume Main     |
         v                                       +-------------------------+
```

#### Servicing Mode Trade-offs
| Attribute | Polling Architecture | Interrupt-Driven Architecture |
| :--- | :--- | :--- |
| **Concurrency** | Purely sequential; no simultaneous process overlap. | High concurrency; supports real-time multi-peripheral events. |
| **CPU Overhead** | $100\%$ core utilization during execution loops. | Zero core utilization during peripheral idle states. |
| **System Latency** | High; downstream devices stall behind busy predecessors. | Low; prioritized preemption immediately branches to urgent tasks. |
| **Execution Penalty** | Nil; zero state-swapping overhead occurs. | Incurs Context Switching Time ($\text{CST}$) on every execution branch. |
| **Ideal Deployment** | Simple, single-task systems with predictable timing. | Multitasking, event-driven, time-critical embedded systems. |

### IV. Interrupt Architecture, Dispatching & Context Switching Dynamics

#### Overview & Theoretical Foundation
Interrupt management requires dedicated hardware arbitration to manage asynchronous operational events safely. An interrupt does not equate to immediate process suspension; rather, it constitutes an external service request. Final dispatch decisions are made by the central interrupt controller based on priority masks and current processor execution states. Because state preemption alters central execution flow, the CPU must serialize its exact dynamic execution snapshot—its *context*—onto a Last-In, First-Out (LIFO) stack before branching to an Interrupt Service Routine (ISR).

#### Mechanics & Operational Invariants
1. **Interrupt Categorization Schemes:**
   * **Vectored vs. Non-Vectored:**
     * *Vectored Interrupts:* Every interrupt source maps directly to a predetermined, fixed memory slot inside an Interrupt Vector Table (IVT). The CPU branches autonomously to this fixed vector address upon request validation.
     * *Non-Vectored Interrupts:* Peripheral ISR addresses are variable. The interrupting hardware device must inject its specific subroutine vector onto the data bus during the handshake phase, or software must poll an identification register to compute the target address.
   * **Maskable vs. Non-Maskable (NMI):**
     * *Maskable Interrupts:* Software control registers can toggle interrupt servicing permissions. Disabling an interrupt does not prevent hardware from setting its status bit in the Pending Register; it simply forces the interrupt controller to ignore the asserted flag.
     * *Non-Maskable Interrupts (NMI):* Hardware inputs that bypass software mask registers. Hard-wired lines reserved for cataclysmic runtime exceptions: hardware bus failures, memory access violations, and the system **Reset** line (which always holds the absolute highest priority across computing architectures).
2. **Interrupt Dispatch & Context Switching Sequence:**
   * **Step 1 (Status Assertion):** Hardware event trips an interrupt condition, latching a logic-1 bit into the CPU's internal **Pending Register**.
   * **Step 2 (Priority Arbitration):** The interrupt controller compares the pending bit's priority rank against other queued bits and the current processor execution threshold.
   * **Step 3 (Context Save - The Push Operation):** If priority dictates immediate servicing, the CPU halts instruction progression. The hardware pushes the **Context** to the thread's allocated Stack Memory:
     * Program Counter ($\text{PC}$, marking the resumption address).
     * Status Register / Program Status Word ($\text{PSW}$).
     * Active General Purpose Registers ($\text{GPRs}$).
   * **Step 4 (Vector Fetch & Execution):** The CPU fetches the ISR entry pointer from the Interrupt Vector Table (IVT) and loads it into the $\text{PC}$.
   * **Step 5 (Callback Mechanics):** To allow user customization of standard interrupt vectors, the system often executes a default low-level handler that dispatches a registered user-defined *callback function*.
   * **Step 6 (Flag Reset):** Prior to or during return, the system or programmer clears the peripheral status flag in the pending/status register. If uncleared, the CPU will immediately re-trigger the same ISR in an infinite loop upon exit.
   * **Step 7 (Context Restore - The Pop Operation):** Upon hitting the Interrupt Return instruction, saved $\text{GPRs}$, status flags, and the original $\text{PC}$ are popped from the stack back into core registers, restoring the interrupted program flow.

```
+-------------------------------------------------------------+
|               Asynchronous Hardware Event Occurs            |

+-------------------------------------------------------------+
```

3. **Software Architecture Constraints on Subroutine Overhead:**
   * Context switching time ($\text{CST}$) introduces system latency and dead execution cycles.
   * Programmers must ensure the computational workload within an invoked function substantially outweighs the overhead of the push/pop stack cycles required to call it.
   * For ultra-short operational routines (1 to 2 lines of execution code), developers must avoid standalone function overhead by implementing **Pre-processor Macros** or **Inline Functions**, eliminating context switching latency entirely.

### V. ARM7 Processor Pipeline & Worst-Case Latency Derivations

#### Overview & Theoretical Foundation
Real-time embedded design requires calculating the maximum permissible delay—the *interrupt latency*—between the hardware assertion of an interrupt and the execution of its first ISR instruction. In the ARM7 RISC architecture, instructions maintain uniform lengths, executing across synchronized clock cycles grouped into machine cycles. If an interrupt occurs while the processor is actively executing an atomic, multi-cycle instruction, the CPU must finish the current instruction and handle bus synchronizations before servicing the request.

#### Mechanics & Operational Invariants
* In the ARM7 processor architecture, processor state tracking is split between the **Current Program Status Register (CPSR)** and the **Saved Program Status Register (SPSR)**.
* Upon acknowledging an interrupt:
  1. The contents of $\text{CPSR}$ are automatically transferred into the corresponding mode's $\text{SPSR}$.
  2. The return address is calculated and preserved.
  3. Appropriate interrupt disable bits are set in the $\text{CPSR}$ to prevent uncoordinated collisions, and the $\text{PC}$ is loaded with the hardware vector address.
* Upon return from the handler:
  1. The saved state residing in $\text{SPSR}$ is restored back into $\text{CPSR}$.
  2. The saved return address is restored back into $\text{PC}$.
  3. The respective peripheral status flag is cleared.

#### Derivation of ARM7 Worst-Case Interrupt Latency
Consider the worst-case operating condition where a higher-priority external interrupt request arrives immediately after the ARM7 processor has committed to a long, atomic instruction cycle:

$$\text{Total Worst-Case Latency Cycles} = C_{\text{exec}} + C_{\text{sync}} + C_{\text{abort}} + C_{\text{state}}$$

Where:
* $C_{\text{exec}} = 20\text{ clock cycles}$ (Maximum duration required to finish the current executing instruction).
* $C_{\text{sync}} = 2\text{ clock cycles}$ (Duration required to synchronize the asynchronous external interrupt signal across internal clock domains).
* $C_{\text{abort}} = 3\text{ clock cycles}$ (Internal bus cycle allocations for data abort handling and pipeline management).
* $C_{\text{state}} = 2\text{ clock cycles}$ (Machine cycles required to update status bits and formally transition the CPU into the interrupt handling state).

Summing these discrete cycles yields the absolute worst-case latency bound:

$$\text{Worst-Case Latency} = 20 + 2 + 3 + 2 = 27\text{ clock cycles}$$

```
Clock Cycle Timeline (Worst-Case ARM7 Scenario):
|<- - - - - - - - - - 20 Cycles - - - - - - - - - ->|<- 2 ->|<- - 3 - ->|<- 2 ->|
+---------------------------------------------------+-------+-----------+-------+
| Execution of current ongoing instruction to completion | Sync  | Data Abort| State |
+---------------------------------------------------+-------+-----------+-------+
^                                                                               ^
|                                                                               |
Interrupt Asserted                                                    First ISR Instruction
(Worst-case boundary)                                                       Fetched
```

*Note on Partial Execution:* If an interrupt is asserted when an instruction has completed $10$ out of its $20$ cycles, the execution delay preceding synchronization drops to the remaining $10$ cycles. The calculation above models the mathematical upper bound ($20$ cycles remaining).

### VI. System Support Hardware: Timers & Real-Time Fundamentals

#### Overview & Theoretical Foundation
Predictable embedded operation relies on specialized timing hardware to enforce bounded execution windows. Microcontroller systems integrate dedicated counter/timer silicon blocks to eliminate software delay loops that would otherwise stall processing cores. At an architectural level, embedded devices aggregate these functional blocks into complex single-die System-on-Chip (SoC) fabrics managed by Real-Time Operating Systems (RTOS), where tasks must execute within strict deterministic deadlines.

#### Hardware Timer Topologies
1. **Interval Timers:**
   * Internal clock-driven counters configured to generate periodic interrupts, precise microsecond/millisecond delays, or Pulse Width Modulation (PWM) wave streams via output-compare channels.
   * Operates conversely in *Input Capture Mode* to register the arrival of external edges, serving as tachometers, frequency counters, or external object passage monitors.
2. **Watchdog Timers (WDT):**
   * Free-running hardware counters driven independently of main application code. The CPU must periodically issue a software reload ("kick" or "feed") to the watchdog register before it reaches zero.
   * If software deadlocks, enters an infinite loop, or hangs on a hardware response (e.g., an ATM user abandoning a terminal mid-transaction without entering a PIN), the counter expires and asserts a master reset signal, restarting system execution from its baseline state.
3. **Brownout Detectors / Timers:**
   * Continuous voltage-monitoring comparators tied directly to the primary power rail.
   * If input voltage drops below a predefined operational threshold, the brownout logic triggers an emergency interrupt. This provides a brief millisecond window for the CPU to enter safe mode, park peripheral actuators, flush register structures, and safely close files before power collapses.

#### Operating Systems vs. Real-Time Operating Systems (RTOS)
| Architectural Attribute | General-Purpose Operating System (GPOS) | Real-Time Operating System (RTOS) |
| :--- | :--- | :--- |
| **Execution Objective** | High computational throughput; fair scheduling. | Absolute temporal determinism and strict deadline adherence. |
| **Temporal Latency** | Soft, non-deterministic latency; tasks yield non-predictable completion times. | Hard bounded latency; missing an execution deadline constitutes a critical system failure. |
| **Task Partitioning** | Kernel space vs. broad user application threads. | Minimal kernel space interacting through structured **Board Support Packages (BSP)** and low-overhead Tasks. |

#### RTOS Task Categorization & Temporal Behaviors
* **Periodic Tasks:** Workloads invoked at deterministic, invariant clock intervals ($T, 2T, 3T, \dots$). Driven by system tick timers.
* **Aperiodic Tasks:** Workloads triggered randomly without predictable spacing between consecutive invocation events.
* **Sporadic Tasks:** Specialized hybrid workloads exhibiting *periodically aperiodic* behavior. Workloads are strictly confined to recur within well-defined operational envelopes or windows, yet trigger unpredictably within those boundaries (e.g., cellular call traffic concentrated within daylight hours, or annual monsoon rain monitoring systems).
* **Critical vs. Non-Critical Tasks:** Critical tasks (e.g., active crash sensors, power rail failure trips) preempt the CPU immediately via high-priority hardware interrupts; non-critical management routines (e.g., system logging, UI redraws) run in remaining background time slices.

#### System-on-Chip (SoC) Integration
To execute real-time task profiles within modern power, size, and cost constraints, discrete boards transition into single-die **Systems-on-Chip (SoC)**. An SoC integrates the primary processing core, Digital Signal Processors (DSP), hardware multimedia encoders/decoders, Direct Memory Access (DMA) controllers, on-chip SRAM/Flash, and an array of physical layer interfaces (USB, Audio, Ethernet, Serial Buses) onto a single silicon substrate.
