## 3. Key Concepts & Definitions

* **Infrastructure as a Service (IaaS):** A foundational cloud service model enabled by hypervisor virtualization that abstracts compute, memory, storage, and networking hardware into dynamically scalable, time-sliced, API-driven virtual services.
* **Elastic Compute Cloud (EC2):** AWS web service providing resizable compute capacity via virtual server instances deployed across globally distributed regions and availability zones.
* **Amazon Machine Image (AMI):** A packaged virtual appliance template containing the operating system, configuration settings, and pre-installed application software required to launch an EC2 instance.
* **Instance Type:** Fixed hardware profiles categorized by family and size that determine the exact allocation of virtual Central Processing Units (vCPUs), physical memory (RAM), storage throughput, and network performance.
* **Graviton Processors:** Custom 64-bit ARM-based microprocessor architectures developed by AWS to deliver optimized price-to-performance over standard x86 (Intel/AMD) architectures.
* **Hypervisor:** The core virtualization firmware/software layer sitting directly above host hardware that creates, abstracts, and isolates multiple virtual operating systems, enforcing memory over-commitment and hardware virtualization.
* **CPU Credits & Bursting:** A performance allocation model utilized in general-purpose burstable instance families (such as T-series) where unused baseline compute accumulates credits, which are spent to burst above baseline capacity during sudden workload spikes.
* **Virtual Private Cloud (VPC):** A logically isolated, user-defined software-defined network (SDN) topology spanning AWS cloud infrastructure, encompassing subnets, route tables, network gateways, and access control policies.
* **Placement Groups:** Logical configurations within an Availability Zone that physically locate EC2 instances close together to enable low-latency, high-throughput network connectivity (exceeding 10 Gbps) for intensive distributed applications.
* **Elastic IP (EIP):** A static, public IPv4 address designed for dynamic cloud computing that can be rapidly remapped across instances to mask host failures, subject to continuous reservation billing when unattached.
* **Elastic Block Store (EBS):** High-performance, persistent, raw block-level storage volumes network-attached to single EC2 instances for transactional operations, databases, and low-latency read/write applications.
* **Simple Storage Service (S3):** A scalable, highly available object storage service organized into regionally defined buckets, storing unstructured data files alongside custom metadata via standard HTTP REST interfaces.
* **Multi-Part Upload:** An S3 data ingestion protocol mandatory for large files (exceeding 5 TB, recommended above 100 MB) that decomposes an object into discrete byte streams uploaded concurrently to maximize throughput and fault tolerance.
* **Write-Once-Read-Many (WORM):** An immutable data storage paradigm characteristic of object stores where an existing object cannot be partially modified; changes require uploading a completely new object version.
* **Amazon S3 Glacier:** A secure, durable, extremely low-cost cloud storage tier engineered for data archiving and long-term regulatory compliance backup with retrieval latencies spanning minutes to hours.
* **Elastic File System (EFS):** A serverless, elastic, network-attached POSIX-compliant shared file storage system accessible concurrently across hundreds of compute instances.
* **Input/Output Operations Per Second (IOPS):** The standard metric quantifying storage device throughput and read/write transaction velocity.

## 4. Detailed Structured Technical Lecture Notes

### I. Cloud Infrastructure & Virtualization Mechanics

* **Shift from Bare-Metal Procurement to IaaS:**
* Traditional on-premise infrastructure lifecycles required extended hardware procurement lead times (often 6–9 months), complex custom import duties, and substantial upfront Capital Expenditures (CapEx).
* IaaS transitions computing to Operational Expenditures (OpEx) through pay-as-you-go provisioning, eliminating fixed geographic and physical constraints.
* Physical hosting facilities are abstracted into global Regions, isolated Availability Zones (AZs), Local Zones, Outposts, and Wavelength edge environments.


* **The Virtualization Engine (Hypervisors):**
* Hypervisors decouple physical hardware from guest operating systems, enabling heterogeneous OS environments (e.g., Windows Server 2025 alongside Linux distributions) to run concurrently on a shared hardware platform.
* *Hardware Emulation & Resource Overcommitment:* Dynamic time-slicing and memory overcommitment allow guest virtual machines to function reliably on minimal allocated hardware footprints (e.g., operating server instances within 1 GB to 2 GB physical RAM allocations) by serving essential operational binaries while swapping idle pages.
* Observed remote desktop (VDI) slowness stems predominantly from transport latency, intermediate hops, and home-network bandwidth bottlenecks rather than hypervisor computational failures.

### II. AWS EC2 Compute Model & Lifecycle

* **EC2 Instance Families & Workload Mapping:**
* AWS segments instances into workload-tailored families:
* *General Purpose:* `M` family (e.g., `M7`, `M7a` for AMD), balanced CPU-to-memory ratios.
* *Burstable General Purpose:* `T` family (e.g., `T2`, `T3`, `T3a`).
* *Compute Optimized:* `C` family, engineered for high-performance processors, batch compute, and distributed processing.
* *Memory Optimized:* `R` family, tailored for in-memory caches, high-volume real-time processing, and big data stores.
* *Accelerated / Storage Optimized:* `I` and `D` families, featuring dense local NVMe/SSD configurations for extreme data throughput.


* *Architecture Variants:* Systems leverage standard x86 Intel processors, AMD chipsets, or AWS-native ARM-based Graviton hardware (which provides cost and energy efficiency gains due to bespoke instruction sets).


* **Burstable Performance & CPU Credit Model:**
* T-series instances run against a continuous baseline compute load.
* Operating below this baseline accumulates *CPU Credits*; operational spikes above the baseline consume credits to avoid execution degradation.
* Depletion of all accumulated credits throttles host CPU execution strictly down to baseline performance until new credits are earned.


* **Instance Sizing Hierarchy:**
* Within an instance family, capacity scales symmetrically across vCPUs and RAM:
* `nano`: $1 \text{ vCPU}, 0.5 \text{ GB RAM}$
* `micro`: $2 \text{ vCPU}, 1 \text{ GB RAM}$
* `medium`: $2 \text{ vCPU}, 4 \text{ GB RAM}$
* `large`: $2 \text{ vCPU}, 8 \text{ GB RAM}$
* `xlarge`: $4 \text{ vCPU}, 16 \text{ GB RAM}$
* `2xlarge`: $8 \text{ vCPU}, 32 \text{ GB RAM}$




* **AMI Sourcing Channels:**
1. *AWS Native / Quick Start:* Base OS images maintained and published directly by AWS (Amazon Linux 2023, Ubuntu, Windows Server, Red Hat, macOS).
2. *Custom / Hardened AMIs:* Created by snapshotting an existing configured instance with specific enterprise security, firewall rules, and proprietary binaries.
3. *AWS Marketplace:* Commercial AMIs bundled with licensed third-party software (e.g., Microsoft SQL Server, specialized database configurations).
4. *VM Import/Export (Uploaded Virtual Servers):* External hypervisor formats (VMware `.vmdk`, Microsoft Hyper-V `.vhd`) converted via cloud migration tooling into AMI representations.


* **Tenancy Models:**
* *Shared Tenancy:* Default multi-tenant virtualization. Multiple customers share underlying physical host hardware isolated via the hypervisor.
* *Dedicated Instances:* Virtual machines running on hardware dedicated to a single customer account, though co-located with other instances belonging to that same customer.
* *Dedicated Hosts:* Full physical server reservation giving complete hardware-level control over instance placement, addressing regulatory compliance and specialized core-based software licensing requirements.


* **Instance Lifecycle Management:**
* States: $\text{Pending} \rightarrow \text{Running} \rightarrow \text{Stopping} \rightarrow \text{Stopped} \rightarrow \text{Terminated}$.
* An instance must be in the **Stopped** state to reconfigure instance types (e.g., upgrading from `t3.micro` to `t3.large`).
* *Billing Traps:* Terminating compute instances does not automatically purge detached EBS block volumes or unassociated Elastic IPs; unattached resources continue to accrue storage and reservation charges.

### III. Cloud Networking, Access Control, and Topology

* **Virtual Private Cloud (VPC) Topology:**
* Provides complete software-defined isolation for cloud resources across Availability Zones.
* Subnet provisioning is governed by Classless Inter-Domain Routing (CIDR) notation. The total available IP space $N_{IP}$ for a prefix length of $n$ is defined by:

$$N_{IP} = 2^{(32 - n)}$$


* Subnets subdivide routing domains across public (Internet-facing via an Internet Gateway) and private networks (accessing outer networks via NAT gateways).


* **Instance Access & Authentication:**
* *Host-Based Firewalls (Security Groups):* Stateful rule engines filtering traffic by protocol (TCP, UDP, ICMP), port, and source IP masks.
* Assigning `0.0.0.0/0` opens incoming ingress to the entire global IPv4 internet space, creating significant security vulnerabilities.
* Secure remote access requires locking inbound traffic to the system operator's specific public IPv4 CIDR block (`/32`).


* *Asymmetric Cryptographic Authentication:*
* Public key is injected into the guest instance upon instantiation; the private key remains secure on the client machine.
* Linux SSH Access operates over TCP Port 22 using PuTTY Private Keys (`.ppk`) or OpenSSH Private Keys (`.pem`).
* Windows RDP operates over TCP Port 3389; Windows local administrator credentials are secure-decrypted by submitting the private `.pem` key against the AWS management console.




* **Addressing Architecture:**
* *Public IPv4:* Ephemeral address dynamically released and modified upon every instance reboot/stop cycle.
* *Private IPv4:* Static internal address retained throughout the lifetime of the network interface within the VPC.
* *Elastic IP (EIP):* Fixed, internet-routable IPv4 address allocated to a cloud account. To mitigate global IPv4 address exhaustion, cloud providers assess hourly billing penalties on any allocated Elastic IP that is not actively bound to a running EC2 instance.


* **High-Speed Placement Groups:**
* Cluster placement strategies position dependent EC2 instances (e.g., API application tiers communicating with dedicated relational database nodes) within immediate physical proximity in a single AZ.
* Enables low-latency interconnects with inter-instance packet transfer speeds scaling in excess of $10\text{ Gbps}$.

### IV. Cloud Storage Systems Taxonomy

* **Storage Paradigms Comparative Breakdown:**

| Parameter | Elastic Block Store (EBS) | Simple Storage Service (S3) | Elastic File System (EFS) | S3 Glacier |
| --- | --- | --- | --- | --- |
| **Storage Architecture** | Block Storage | Object Storage | Distributed File System | Archival Object Store |
| **Data Unit** | Fixed-size disk blocks / chunks | Unstructured objects + metadata | Hierarchical files & folders | Vault archives / objects |
| **Access Model** | Single instance attachment via SAN | Global RESTful API endpoints | Multi-instance shared POSIX mount | Batch job retrieval API |
| **I/O Performance** | High IOPS, sub-millisecond read/write | High throughput, web latencies | Elastic throughput, concurrent access | High latency (minutes to hours) |
| **Primary Use Cases** | OS boot disks, active RDBMS volumes | Static assets, media, raw big data | Content management, clustered analytics | Regulatory and long-term tape backup |
| **Modification Model** | Granular byte/block modifications | Write-Once-Read-Many (WORM) | Traditional file read/write locking | Immutable archival storage |

* **Deep Dive: Block vs. Object Storage:**
* *Block Storage Mechanics:* Data is split across raw sector-aligned storage blocks (typically 512-byte or 4 KB increments). Modifications are executed purely at the specific chunk level—if an application modifies a single data byte, the operating system file system driver writes exclusively to that targeted block, ensuring minimal latency and high efficiency for transactional systems.
* *Object Storage Mechanics:* Data is written as a complete entity paired with system/custom metadata headers within a flat namespace bucket. Because direct byte patching is unavailable, modifying a file requires reading, mutating, and rewriting the entire object stream back to the bucket via HTTP API methods (`PUT`, `GET`, `DELETE`).


* **Object Limits & Ingestion Thresholds:**
* S3 enforces a maximum single-object capacity limit of $5\text{ TB}$.
* Objects exceeding $100\text{ MB}$ to $5\text{ TB}$ must utilize **Multi-Part Upload**, splitting the stream into chunks transferred concurrently to mitigate network dropouts.


* **Cloud Storage Cost Dynamics:**
* Storage accounts accrue charges based on two distinct metrics:
1. *Data at Rest:* Baseline capacity pricing per GB-month for data preserved on underlying media.
2. *Data in Motion / Operations:* Per-request API charges (`GET`/`PUT` requests) combined with external data egress bandwidth fees assessed per gigabyte transferred across internet gateways.


* Proactive cost containment requires the setup of **CloudWatch/Billing Alarms** configured at defined utilization thresholds (e.g., warning triggers when usage exceeds 40% of budgeted credit allocations).
