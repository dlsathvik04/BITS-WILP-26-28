# Lecture Study Material: 02 Data Modeling and Normalization

## 1. Core Topics For Self Study

- **The Entity-Relationship (ER) Model:** Understanding the fundamental building blocks of database design, including entities, attributes, and relationships.
- **Attribute Classification:** Categorizing properties into simple, composite, single-valued, multi-valued, and derived types.
- **Weak Entities and Identifying Relationships:** Defining entities that lack independent existence and how they are linked to "owner" entities.
- **Relationship Constraints:** Analyzing cardinality ratios (1:1, 1:N, M:N) and participation constraints (Total vs. Partial).
- **ER-to-Relational Mapping:** The step-by-step process of converting visual ER diagrams into structured database tables.
- **Database Normalization:** The systematic process of refining table structures to eliminate data redundancy and prevent update, insertion, and deletion anomalies.
- **Normal Forms (1NF, 2NF, 3NF):** Learning the specific rules for each level of normalization to ensure data integrity and storage efficiency.

## 2. Key Concepts & Definitions

- **Entity Type:** A real-world object or concept (e.g., Student, Employee) represented in a database, typically visualized as a rectangle.
- **Attribute:** A property or characteristic of an entity (e.g., Name, Salary), visualized as an oval.
- **Primary Key:** A unique identifier for an entity instance (underlined in diagrams).
- **Composite Attribute:** An attribute that can be divided into smaller sub-parts (e.g., Name into First, Middle, and Last).
- **Multi-valued Attribute:** An attribute that can have more than one value for a single entity instance (e.g., Phone Numbers), represented by a double oval.
- **Derived Attribute:** An attribute whose value is calculated from other attributes (e.g., Age from Date of Birth), represented by a dashed oval.
- **Weak Entity:** An entity that cannot be uniquely identified by its own attributes alone and depends on a strong entity (owner), represented by a double rectangle.
- **Partial Key (Discriminator):** An attribute of a weak entity that, combined with the owner's primary key, uniquely identifies instances. Represented with a dotted underline.
- **Cardinality Ratio:** Specifies the maximum number of relationship instances an entity can participate in (1:1, 1:N, M:N).
- **Participation Constraint:** Specifies whether every entity in the set must participate in a relationship (Total Participation = double line; Partial Participation = single line).
- **Insertion Anomaly:** Being unable to add data to the database because some required attributes are missing.
- **Deletion Anomaly:** The unintended loss of data when a record is deleted.
- **Update Anomaly:** Data inconsistency caused by redundant data being updated in one place but not another.
- **Normalization:** The process of decomposing tables to minimize redundancy and dependency.
- **First Normal Form (1NF):** Requires that every attribute contains only atomic (indivisible) values.
- **Second Normal Form (2NF):** Requires 1NF and that every non-prime attribute is fully functionally dependent on the entire primary key (no partial dependencies).
- **Third Normal Form (3NF):** Requires 2NF and that no non-prime attribute is transitively dependent on the primary key.

## 3. Detailed Structured Lecture Notes

### I. Introduction to Data Modeling
- **Data Modeling:** The process of identifying real-world objects, their properties, and their associations to design a database.
- **Objective:** Provides a visual representation (Conceptual Design) of requirements before physical implementation.
- **Benefits:** Reduces redundancy, improves consistency, and simplifies communication between designers and developers.

### II. The ER Model Components
- **Entities:** Represented by **Rectangles**.
- **Attributes:** Represented by **Ovals**.
    - **Simple:** Indivisible.
    - **Composite:** Divided into meaningful sub-components.
    - **Multi-valued:** Can hold multiple values (e.g., a department with multiple locations).
    - **Derived:** Calculated values (e.g., "Number of Employees" in a department).
- **Weak Entities:** 
    - Lacks a primary key.
    - Uses a **Double Rectangle**.
    - Connected via an **Identifying Relationship** (**Double Diamond**).
    - Example: "Dependent" entity depends on "Employee" entity.

### III. Relationship Constraints
- **Cardinality:**
    - **1:1 (One-to-One):** One instance of A links to one instance of B (e.g., Employee manages Department).
    - **1:N (One-to-Many):** One instance of A links to many of B (e.g., Department has many Employees).
    - **M:N (Many-to-Many):** Many instances of A link to many of B (e.g., Employees work on many Projects).
- **Participation:**
    - **Total:** Every entity instance must participate (e.g., every Department must have a Manager).
    - **Partial:** Participation is optional (e.g., not every Employee is a Manager).

### IV. Converting ER Diagrams to Tables (Mapping)
- **Entities to Tables:** Each strong entity becomes a table.
- **Weak Entities:** The table includes the weak entity’s attributes plus the primary key of the owner entity as a foreign key. The primary key of the new table is a composite of both.
- **Relationships:**
    - **1:1:** Add the primary key of one table as a foreign key in the other (usually in the table with total participation to avoid nulls). Alternatively, merge the tables if both have total participation.
    - **1:N:** Add the primary key of the "One" side as a foreign key in the "Many" side table.
    - **M:N:** Create a separate "cross-reference" table containing the primary keys of both participating entities as foreign keys.
- **Multi-valued Attributes:** Create a separate table to store the values and link them back to the original entity's primary key.

### V. Normalization and Normal Forms
- **The Goal:** Eliminate anomalies (Insertion, Update, Deletion) and redundancy.
- **1NF (Atomic Values):**
    - Eliminate multi-valued attributes and repeating groups.
    - Example: Instead of a list of phone numbers in one cell, create multiple rows or a separate table.
- **2NF (Full Functional Dependency):**
    - No partial dependencies. If a primary key is composite (A, B), a non-prime attribute C cannot depend only on A.
    - Solution: Decompose into separate tables.
- **3NF (No Transitive Dependency):**
    - Non-prime attributes should not depend on other non-prime attributes.
    - Example: If SSN determines Dept_Number, and Dept_Number determines Dept_Name, there is a transitive dependency (SSN -> Dept_Name). 
    - Solution: Move Dept_Number and Dept_Name to a separate "Department" table.

## 4. Discussion & Q&A Highlights

**Q: Can an entity be uniquely identified by its own attributes but still be a weak entity?**
**A:** No. If it can be uniquely identified by its own attributes within the context of the database, it is a strong entity. A weak entity, by definition, lacks sufficient attributes to form a primary key on its own.

**Q: Why don't we include the 'Name' and its components (FName, LName) together in the table?**
**A:** It depends on the queries. If you frequently need to search by Last Name, storing them as separate attributes (1NF) is better. If the application only ever needs the full string, storing it as one is acceptable, but usually, atomic decomposition is preferred for flexibility.

**Q: In the 'Supervises' relationship, why is participation partial on both sides?**
**A:** In most organizations, the CEO or top leadership does not have a supervisor (partial on the supervised side), and entry-level employees do not supervise anyone (partial on the supervisor side).

**Q: Why do we create a third table for Many-to-Many (M:N) relationships instead of using foreign keys?**
**A:** Using foreign keys in M:N would lead to massive data redundancy and a violation of 1NF. If one employee works on five projects, you would have to repeat the employee's entire row five times to list each project ID. A separate table only repeats the IDs, saving significant space.

**Q: Regarding the 'Managers' relationship, the instructor mentioned a correction about the double line. What was it?**
**A:** The diagram initially showed a double line (total participation) for Employees in the "Manages" relationship. The instructor corrected this, stating it should be a single line (partial) because not every employee is a manager. However, from the Department side, it remains total participation because every department must have a manager.

   a) Composite attribute
   b) Multi-valued attribute
   c) Derived attribute
   d) Primary key

### Answer Key for MCQs
1. **b) Dashed Oval** (Used for attributes calculated from others).
2. **b) In the Employee table** (The 'Many' side holds the foreign key to avoid repeating department data).
3. **b) Double Rectangle** (Double ovals are multi-valued; double diamonds are identifying relationships).
4. **b) 2NF** (1NF is about atomicity; 3NF is about transitive dependencies).
5. **c) Derived attribute** (It is derived from the "Date of Birth").

### Short-Answer Conceptual Problems

1. **Explain the difference between a Deletion Anomaly and an Update Anomaly.**
   *Sample Answer:* A deletion anomaly occurs when deleting a record results in the unintended loss of other unrelated data (e.g., deleting the last employee in a department also deletes the only record of that department's existence). An update anomaly occurs when redundant data is stored; if the data is updated in one row but not others, the database becomes inconsistent.

2. **Why is 3NF preferred over 2NF?**
   *Sample Answer:* 3NF is superior because it removes transitive dependencies. Even if a table is in 2NF (no partial dependencies), a non-prime attribute might still depend on another non-prime attribute. This causes redundancy. 3NF ensures that all non-prime attributes depend only on the primary key, further reducing anomalies.

3. **How do you map a Many-to-Many (M:N) relationship to a relational schema?**
   *Sample Answer:* To map an M:N relationship, you must create a new table. This table contains the primary keys of both participating entities as foreign keys. Usually, the combination of these two foreign keys serves as the composite primary key for the new table. Any attributes attached to the relationship itself (e.g., 'Hours Worked' on a project) are also added to this new table.
