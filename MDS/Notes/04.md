- **Transaction Management & States:** The lifecycle of a database transaction from the "Active" state to "Committed" or "Aborted."

- **Distributed Database Architectures:** Differences between Homogeneous and Heterogeneous systems, and the role of Global versus Local Schemas.

## 2. Key Concepts & Definitions

- **Cartesian Product (Cross Join):** A join operation without a condition that results in every row of the first table being paired with every row of the second table ($M \times N$ records).
- **Inner Join:** A join that retrieves only the records where there is a match in both tables based on a specified condition.
- **Outer Join (Left/Right/Full):** Joins that include matching records plus non-matching records from either the left, right, or both tables (with NULLs filling the gaps).
- **Subquery:** A query nested within another SQL query, where the results of the inner query are used by the outer query.
- **Transaction:** A sequence of one or more SQL operations treated as a single logical unit of work.
- **Atomicity:** The "all or nothing" property; either the entire transaction is completed, or none of it is applied.
- **Consistency:** Ensuring a transaction transforms the database from one valid state to another, maintaining all predefined rules/constraints.
- **Isolation:** Ensuring that concurrently executing transactions do not interfere with each other.
- **Durability:** The guarantee that once a transaction is committed, its changes are permanent, even in the case of a system failure.
- **Schema Evolution:** The process of modifying a database's structure (metadata) over time to meet new business requirements.
- **Denormalization:** The intentional introduction of redundancy into a database to improve read performance by reducing the number of necessary joins.
- **Horizontal Scaling:** Increasing capacity by adding more machines to a system (common in distributed databases).
- **Vertical Scaling:** Increasing capacity by adding more power (CPU, RAM) to an existing single machine.

## 3. Detailed Structured Lecture Notes

### I. SQL Joins and Cartesian Products
- **Cartesian Product (Cross Join):**
    - Occurs when two tables are joined without any `WHERE` or `ON` condition.
    - If Table A has $M$ records and Table B has $N$ records, the result is $M \times N$ records.
    - Most of these records are practically meaningless in a real-world context.
- **Inner Join:**
    - Effectively a filtered Cartesian product.
    - Matches records based on a common attribute (e.g., `Student_ID`).
    - Only matching rows appear in the final result.
- **Outer Joins:**
    - **Left Outer Join:** Includes all matching records plus all non-matching records from the "Left" table. Attributes from the "Right" table are filled with NULL for non-matches.
    - **Right Outer Join:** Includes all matching records plus all non-matching records from the "Right" table.
    - **Full Outer Join:** Includes all records from both tables. 
    - *Note:* MySQL does not natively support `FULL OUTER JOIN`. It must be implemented using a `UNION` of a `LEFT JOIN` and a `RIGHT JOIN`.

### II. Subqueries (Nested Queries)
- **Logic of Execution:** 
    - The **Inner Query** executes first.
    - Its result set is passed to the **Outer Query**, which then filters its results based on that set.
- **Single-row vs. Multi-row Subqueries:**
    - Single-row subqueries return one value (e.g., finding students with a GPA higher than the *average*).
    - Multi-row subqueries return a list (e.g., finding all students enrolled in a specific *course ID*).

### III. Transaction Management
- **Definition:** A logical unit of work (e.g., a bank transfer).
- **Transaction States:**
    - **Active:** The initial state where read/write operations occur.
    - **Partially Committed:** Operations are finished, but changes are in the "Log" and not yet finalized in the main database.
    - **Committed:** The transaction is successfully finalized; changes are permanent.
    - **Failed:** An error occurs during execution.
    - **Aborted:** The transaction is rolled back to the pre-transaction state.
    - **Terminated:** The final state after either committing or aborting.
- **Concurrency & Deadlocks:** 
    - When multiple transactions wait for resources held by each other, a "Deadlock" occurs.
    - The system must abort one transaction to break the cycle and allow others to proceed.

### IV. ACID Properties
- **Atomicity:** Prevents "half-done" transactions. Example: Money is debited from Account A but not credited to Account B.
- **Consistency:** Database constraints (like primary keys or non-null fields) must remain valid after the transaction.
- **Isolation:** Prevents "dirty reads" or "lost updates" where one transaction sees the uncommitted work of another.
- **Durability:** Relies on logs to ensure that even if a server crashes immediately after a commit, the data can be recovered.

### V. Database Design: Evolution & Denormalization
- **Schema Evolution:** 
    - As applications grow, new attributes (columns) are added.
    - Use migration scripts and version control to manage changes systematically.
- **Denormalization:**
    - Normalized tables (3NF/BCNF) are great for storage efficiency and data integrity.
    - However, for "Read-Heavy" analytical queries, joining 10 normalized tables is too slow.
    - Denormalization combines tables into one to avoid joins, sacrificing storage for speed.

### VI. Distributed Databases
- **Motivations:**
    - Avoiding a single point of failure (centralized server crash).
    - Reducing latency by placing data geographically closer to users.
- **Architecture:**
    - **Local Transaction:** A transaction that only needs data from the site where it was initiated.
    - **Global Transaction:** A transaction requiring data from multiple sites.
    - **Global Schema:** Every site in a distributed system needs the full schema definition to validate queries, even if it doesn't hold all the data locally.
- **Types of Distributed Systems:**
    - **Homogeneous:** Same DBMS and same data model at every site.
    - **Heterogeneous:** Different DBMS (e.g., one site uses MySQL, another Oracle) or different data models.
    - **Multi-database Systems:** Integrating pre-existing, independent databases (common in corporate mergers). Communication is often handled via APIs or middleware.
