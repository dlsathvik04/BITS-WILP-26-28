## 3. Key Concepts & Formal Definitions

| Concept / Term | Formal Definition & Operational Meaning | Contextual Constraints / Properties |
| :--- | :--- | :--- |
| **Distributed Database (DDB)** | A collection of multiple, logically interrelated databases distributed physically over a computer network rather than isolated on a single machine. | Data must not be arbitrary collections; it must maintain logical cohesion and appear as a unified system to the client. |
| **Distributed DBMS (DDBMS)** | The software system that manages the distributed database while providing transparent access mechanisms, transaction management, inter-site communication, and coordination. | Must abstract distribution details so queries execute without requiring explicit network host parameters from the client. |
| **Distribution Transparency** | An architectural property ensuring the physical location, fragment boundaries, and replication factors of data remain invisible to applications and end-users. | End users interact with a global logical schema using standard SQL without specifying individual node sites. |
| **Local Autonomy** | The capability of an individual participating site in a distributed network to retain administrative control and independently execute operations on locally resident data. | Systems should be partitioned to minimize remote network coordination, thereby bounding latency and isolating local failures. |
| **Horizontal Fragmentation** | The partitioning of a relation $R$ into subsets of tuples (rows) based on specified predicate selection criteria. | Must satisfy the completeness requirement: the union of all horizontal fragments must reconstitute the original relation $R$. |
| **Derived Horizontal Fragmentation** | The partitioning of a child relation based on the horizontal fragmentation predicate of a related parent relation, executed via a semi-join or equi-join. | Requires an active relational link (foreign key to primary key relationship) between the parent and child tables. |
| **Vertical Fragmentation** | The partitioning of a relation $R$ into subsets of attributes (columns), keeping subsets of columns accessed together in common storage fragments. | Requires that the primary key attribute(s) of $R$ be duplicated across all vertical fragments to guarantee lossless join reconstruction. |
| **Union Compatibility** | A formal relational condition where two relations share identical attribute arity (degree) and identical corresponding data type domains. | Required to apply the set union operator ($\cup$) for horizontal reconstruction; dissimilar domains cannot be unioned. |
| **Strict Quorum Consensus** | A parameter configuration in leaderless replication systems where write quorum $w$ and read quorum $r$ over $N$ total replica nodes satisfy $w + r > N$. | Guarantees by the pigeonhole principle that the set of nodes written to and the set of nodes read from overlap by at least one node containing the latest write. |

## 4. Detailed Structured Technical Lecture Notes

### I. Motivation and Distributed System Fundamentals

#### Overview & Theoretical Foundation
Traditional database systems utilize a centralized architecture wherein all data structures, transaction processing engines, and query execution threads reside on a singular monolithic machine. As enterprise organizations evolved into geographically distributed multi-campus universities and multinational technology firms, centralized systems created structural bottlenecks. Monolithic setups present a critical single point of failure (SPOF): if the central host experiences hardware termination or network severance, global transaction processing halts entirely. 

Furthermore, routing all global client queries to a central geographical location introduces propagation delay and high communication overhead. Distributed systems address these constraints through data localization and network processing.

#### Mechanics & Operational Invariants
1. **Physical Distribution vs. Logical Cohesion:**
   A distributed database physically deploys data chunks across distinct sites (nodes, servers, branch offices, or data centers) linked via local or wide area networks. Physical distribution alone does not constitute a distributed database; the data must remain logically interrelated under a global conceptual schema managed by a DDBMS layer.
2. **Scaling Paradigms:**
   * **Vertical Scalability ($1\times \to 2\times \to 4\times$):** Scaling monolithic servers requires upgrading memory (RAM), storage volumes, and compute processing capability on a single machine. This hardware ceiling induces prohibitive costs and persistent SPOF risks.
   * **Horizontal Scalability (Modular / Incremental Growth):** Distributed topologies scale by appending autonomous nodes (Site $N+1$) to the network. Processing capacity and storage increase modularly without taking operational nodes offline.

```
Monolithic (Vertical)             Distributed (Horizontal Modular)
   +--------------+                 +--------+       +--------+
   |  Central DB  |                 | Site 1 |<----->| Site 2 |
   |  [RAM/CPU++] |                 +--------+       +--------+
   +--------------+                     ^                ^
         /    \                         |    Network     |
      Req      Req                      v                v
     /            \                 +--------+       +--------+
Client 1        Client 2            | Site 3 |<----->| Site 4 |
                                    +--------+       +--------+
```

3. **Autonomy and Localization:**
   System partitioning assigns data to sites where access frequency is maximized (e.g., Delhi customer data stored on the Delhi server, Mumbai customer data on the Mumbai server). Queries originating in Delhi execute locally on the local server without traversing inter-city wide area network links, bypassing network latency.

#### Complexity & Structural Analysis
| Architecture Dimension | Centralized Database | Distributed Database |
| :--- | :--- | :--- |
| **Storage Topology** | Single physical machine | Multiple distinct network-connected sites |
| **Processing & Control** | Centralized processor & memory | Distributed across autonomous nodes |
| **Administrative Complexity** | Low (unified local OS/engine) | High (inter-site synchronization & consensus) |
| **Failure Vulnerability** | SPOF: single failure causes total outage | Fault tolerant: $N-1$ nodes process if 1 fails |
| **Expansion Mechanics** | Vertical scaling (hardware replacement) | Horizontal scaling (node insertion) |
| **Client Access Channel** | Direct LAN/WAN to centralized host | Transparent routing via DDBMS abstraction layer |

#### Design Trade-offs & Limitations
Distributing database components trades architectural simplicity for operational latency management. Centralized systems have zero network communication latency for internal transactions, but scale poorly and fail catastrophically. Distributed databases improve availability, fault tolerance, and localized read performance, but introduce significant communication overhead, multi-site failure handling states, distributed deadlock risks, and distributed security surfaces.

### II. DDBMS Architecture and Classification Topologies

#### Overview & Theoretical Foundation
The Distributed Database Management System (DDBMS) acts as a coordination and translation layer between end-users and distributed physical databases. The DDBMS enforces distribution transparency: application developers interact with the database via standard query syntax without embedding physical site addresses or manual data routing logic. 

#### Mechanics & Operational Invariants
Distributed database architectures classify into three primary models depending on software similarity, data model identity, and site autonomy:

```
                      +-----------------------------+
                      |   DDBMS Architectural Tree   |
                      +-----------------------------+
                                     |
         +---------------------------+---------------------------+
         |                                                       |
+------------------+                                   +-------------------+
|   Homogeneous    |                                   |   Heterogeneous   |
+------------------+                                   +-------------------+
| Same DBMS Engine |                                   | Diverse Engines   |
| Same Data Model  |                                   | Query Translation |
+------------------+                                   +-------------------+
                                                                 |
                                                       +-------------------+
                                                       |  Multi-Database   |
                                                       |     (MDBS)        |
                                                       +-------------------+
                                                       | Autonomous Legacy |
                                                       | Integration Layer |
                                                       +-------------------+
```

1. **Homogeneous DDBMS:**
   * Every node operates the identical DBMS software package (e.g., all nodes run MySQL, or all run PostgreSQL) and adheres to an identical data model (relational).
   * Coordination and integration overhead are low; queries split into sub-queries execute natively across sites without dialect translation.
2. **Heterogeneous DDBMS:**
   * Participating sites implement different DBMS products (e.g., Site 1 runs MySQL, Site 2 runs PostgreSQL, Site 3 runs Oracle) or divergent schemas.
   * The DDBMS must provide semantic and syntactic translation layers. A global query must be broken down and converted into the specific dialect, type system, and schema representation of each target site.
3. **Multi-Database Systems (MDBS):**
   * Arises primarily through corporate acquisitions where distinct, fully formed database systems with high local autonomy must be federated without decommissioning legacy platforms.
   * Autonomous database engines remain fully independent; integration occurs via a loose software abstraction layer without tight centralized operational coupling.

#### Transaction Execution Mechanics
* **Local Transactions:** A transaction referencing and modifying data items situated exclusively at the local site where the query was submitted. Processed directly by the local DBMS engine with zero external network overhead.
* **Global Transactions:** A transaction referencing data items distributed across two or more physical sites, or requiring distributed write synchronization. The site where the query is received acts as the Global Transaction Manager (Coordinator), segmenting the request into localized sub-queries, dispatching them over the network, monitoring execution states, and managing distributed commit/abort logic.

### III. Data Fragmentation Principles and Relational Operations

#### Overview & Theoretical Foundation
Data partitioning, or fragmentation, consists of decomposing logical database relations into smaller, structurally manageable subsets (fragments) that can be individually allocated across network nodes. The objective of fragmentation is optimizing locality of reference: placing data physically proximate to the applications that query it most frequently. 

Under the principle of spatial and temporal locality (derived from fundamental computer architecture), execution processes access correlated addresses repeatedly over execution intervals. By fragmenting tables to match enterprise usage patterns, inter-site bandwidth consumption is minimized, and parallel processing of mutually exclusive data subsets is unlocked.

#### Mechanics & Operational Invariants

```
Original Table [Employee: SSN, Name, Dept, Salary, Contact, Location]
  │
  ├── Horizontal Fragmentation (Row Predicate Selection: σ)
  │     ├── Fragment 1: σ Location='Delhi' (Employee)
  │     └── Fragment 2: σ Location='Mumbai' (Employee)
  │     [Reconstruction: Fragment 1 ∪ Fragment 2]
  │
  ├── Vertical Fragmentation (Attribute Projection: π with Shared Primary Key)
  │     ├── Fragment 1: π SSN, Name, Dept (Employee)
  │     └── Fragment 2: π SSN, Salary, Contact (Employee)
  │     [Reconstruction: Fragment 1 ⨝ Fragment 2 on SSN]
  │
  └── Derived Horizontal (Child Partitioning via Parent Join: ⨝)
        ├── Dep4 = σ Dnumber=4 (Department)
        └── Emp_Dept4 = Employee ⨝ Dnumber=Dnumber Dep4
```

1. **Primary Horizontal Fragmentation:**
   * Segments relation $R$ along its horizontal dimension (records/tuples) via relational algebra selection ($\sigma$):
     $$R_i = \sigma_{C_i}(R)$$
     where $C_i$ is a selection condition predicated on relation attributes.
   * Example: Segmenting an `Employee` relation based on operational region:
     $$\text{Emp}_{\text{Delhi}} = \sigma_{\text{Location} = \text{'Delhi'}}(\text{Employee})$$
     $$\text{Emp}_{\text{Mumbai}} = \sigma_{\text{Location} = \text{'Mumbai'}}(\text{Employee})$$
   * **Reconstruction Invariant:** Horizontal fragmentation must guarantee completeness. The original relation must be reconstructible using the relational set union ($\cup$) operator without data loss or spurious tuples:
     $$\text{Employee} = \text{Emp}_{\text{Delhi}} \cup \text{Emp}_{\text{Mumbai}}$$
   * Reconstruction via set union requires strict **Union Compatibility**: fragments must possess the identical degree (number of attributes) and identical attribute domains in corresponding positions.
2. **Derived Horizontal Fragmentation:**
   * Partitions a relation based on the horizontal selection conditions applied to an associated, foreign-key-linked relation.
   * Let a parent relation `Department` be partitioned into departmental fragments:
     $$\text{Dept}_4 = \sigma_{\text{Dnumber} = 4}(\text{Department})$$
     $$\text{Dept}_5 = \sigma_{\text{Dnumber} = 5}(\text{Department})$$
   * The associated child relation `Employee` is partitioned via an equi-join ($\Join$) on the matching linking attribute:
     $$\text{Emp}_{\text{Dept4}} = \text{Employee} \Join_{\text{Dnumber} = \text{Dnumber}} \text{Dept}_4$$
     $$\text{Emp}_{\text{Dept5}} = \text{Employee} \Join_{\text{Dnumber} = \text{Dnumber}} \text{Dept}_5$$
   * Natural joins ($\ast$) can also be utilized if attribute schemas share identical nomenclature, automatically equating join predicates. Reconstructing $\text{Employee}$ occurs via union across derived horizontal components:
     $$\text{Employee} = \text{Emp}_{\text{Dept4}} \cup \text{Emp}_{\text{Dept5}}$$
3. **Vertical Fragmentation:**
   * Segments relation $R$ along its vertical dimension (attributes/columns) via relational algebra projection ($\pi$):
     $$R_i = \pi_{\text{Attribute\_List}_i}(R)$$
   * Columns accessed together by localized application services are encapsulated within a discrete vertical partition (e.g., identity data separated from payroll data):
     $$\text{Emp}_1 = \pi_{\text{EmpID, Name, Dept}}(\text{Employee})$$
     $$\text{Emp}_2 = \pi_{\text{EmpID, Salary, Contact}}(\text{Employee})$$
   * **Lossless Join Invariant:** Relational projection discards attribute bindings across fragments. To prevent total loss of structural correlation, **the relation's primary key must be explicitly replicated in every vertical fragment**.
   * Reconstitution cannot occur via union because vertical fragments fail union compatibility (divergent column types and counts). Reconstruction requires an equi-join on the replicated primary key:
     $$\text{Employee} = \text{Emp}_1 \Join_{\text{EmpID} = \text{EmpID}} \text{Emp}_2$$
4. **Mixed (Hybrid) Fragmentation:**
   * Successive application of horizontal and vertical partitioning schemes. A table is first segmented horizontally by regional boundaries ($\sigma_{\text{Location}}$), and each resulting regional fragment is further partitioned vertically ($\pi_{\text{Attributes}}$) into operational and financial subsets. Reconstruction requires nested compositions of joins and unions.

### IV. Data Allocation and Replication Topologies

#### Overview & Theoretical Foundation
Following fragmentation, fragments must be assigned to physical system sites via an allocation strategy. Allocation schemes dictate data availability, storage utilization, and network traffic profiles. Strategies range from non-replicated partitioning to complete global replication. When replicas are introduced, the system must establish update propagation mechanisms to govern whether modifications persist synchronously across all sites or propagate asynchronously.

#### Mechanics & Operational Invariants
1. **Allocation Strategies:**
   * **Non-Replicated (Partitioned) Allocation:** Exactly one copy of each fragment exists globally, assigned to a single site. Minimizes storage overhead and write operational cost (single localized write). If the hosting site fails, the contained fragment becomes completely unavailable until physical restoration occurs.
   * **Fully Replicated Allocation:** A complete copy of the entire database (or all fragments) resides locally at every participating site in the network. Read operations are entirely local ($\Omega(1)$ network communication overhead). However, write operations incur maximum latency and system overhead, as an update applied to one node must be synchronized across all remaining network nodes.
   * **Partially Replicated Allocation:** High-frequency read fragments or mission-critical segments are replicated at multiple target sites, while specialized fragments reside only at single localized sites. Provides an operational balance between read availability and write synchronization cost. Standard production frameworks frequently configure a default replication factor of three ($RF = 3$).

```
Replication Topologies:

A. Single-Leader (Leader-Follower)
   Writes ────> [ Leader Node ] ────Sync/Async Updates────> [ Follower 1 ]
                     │
                     └────────────────────────────────────> [ Follower 2 ]
   Reads  <─── Served by Leader or Followers ──────────────

B. Multi-Leader (Active-Active)
   Region A Writes ──> [ Leader A ] <─── Async Inter-Leader ───> [ Leader B ] <── Region B Writes
                              │           Replication Sync            │
                              v                                       v
                        [ Followers A ]                         [ Followers B ]

C. Leaderless (Quorum Consensus)
   Client Writes ─── Direct parallel dispatch (w nodes) ───> [ Node 1 ] [ Node 2 ] [ Node 3 ]
   Client Reads  ─── Direct parallel dispatch (r nodes) ───> [ Node 1 ] [ Node 2 ] [ Node 3 ]
```

2. **Replication Propagation Mechanics:**
   * **Synchronous Replication:** The coordinator node does not acknowledge write completion to the client until every designated replica node processes the update and returns an acknowledgment. Guarantees absolute consistency across copies, but subjects write transactions to the slowest replica node or severed network link.
   * **Asynchronous Replication:** The primary node applies the update locally, returns an immediate success status to the client, and enqueues the update for background propagation to secondary replicas. Dramatically reduces write latency, but introduces a transient replication lag where secondary replicas hold stale data, creating risks of temporal inconsistency.
3. **Replication Topologies:**
   * **Single-Leader (Primary-Secondary):** All write requests route strictly to the designated primary (leader). The leader writes locally and streams updates to secondary followers. Read requests scale horizontally by load-balancing across followers. If the leader fails, distributed consensus protocols promote a follower to primary status.
   * **Multi-Leader (Active-Active):** Multiple nodes act as designated write leaders (typically distributed across geographical zones). Writes are local to each regional leader and replicated across remote leaders asynchronously. This introduces **Write Conflicts**: if Client 1 updates attribute $X$ to $100$ at Leader A while Client 2 concurrently updates $X$ to $200$ at Leader B, both leaders accept their valid local writes. Reconciling conflicting states during inter-leader synchronization requires conflict resolution policies, such as timestamp ordering (Last-Write-Wins).
   * **Leaderless Replication:** Eliminates coordinator bottlenecks entirely. Clients dispatch writes directly to multiple peer replica nodes in parallel. Write and read success boundaries are governed by algorithmic quorums.

#### Quantitative Quorum Analysis (Leaderless Topologies)
To maintain consistency and guarantee that stale data is never surfaced to client queries in a leaderless system, the read and write operational parameters must obey the strict quorum intersection inequality:

$$w + r > N$$

Where:
* $N$ = Total number of storage replica nodes for the designated data fragment.
* $w$ = Write quorum: the minimum count of replica nodes that must process and acknowledge a write operation before declaring it successful.
* $r$ = Read quorum: the minimum count of replica nodes that must be queried concurrently before synthesizing the returned data value.

```
N = 9 Replicas Topology (Pigeonhole Overlap Example)
Total Nodes: 9
Quorum Configuration: w = 5, r = 5
Condition Check: w + r = 10 > 9 (Satisfied)

[ W1 ] [ W2 ] [ W3 ] [ W4 ] [ W5* ] [ N6 ] [ N7 ] [ N8 ] [ N9 ]
| <────── Written Set (5) ──────> |
                            | <─────── Read Set (5) ────────> |
                            [ R1* ] [ R2 ] [ R3 ] [ R4 ] [ R5 ]

Result: Node 5 (*) is an invariant overlapping member containing the latest update.
```

If $w + r > N$, then by the pigeonhole principle, the set of nodes containing acknowledged writes and the set of nodes queried during a read operation must intersect by at least one node:

$$\{ \text{Nodes Written} \} \cap \{ \text{Nodes Read} \} \neq \emptyset$$

When $N = 9$, configuring strict majority quorums requires:

$$w = \lceil (N + 1) / 2 \rceil = \lceil 10 / 2 \rceil = 5$$
$$r = \lceil (N + 1) / 2 \rceil = 5$$
$$w + r = 5 + 5 = 10 > 9$$

If five nodes acknowledge a write transforming record $X$ from $50$ to $100$, four nodes remain at the stale value $50$. Any read operation querying five nodes is mathematically guaranteed to inspect at least one updated node holding value $100$. By comparing version attributes or timestamps across the five read samples, the client identifies and discards the stale values ($50$), preserving correctness.

#### Design Trade-offs & Replication Selection
| Dimension / Strategy | Non-Replicated | Partially Replicated | Fully Replicated |
| :--- | :--- | :--- | :--- |
| **Storage Footprint** | Minimal ($1\times$) | Moderate ($1\times < \text{Footprint} < N\times$) | Maximum ($N\times$) |
| **Read Performance** | Local only at resident site | High for replicated fragments | Maximized ($\Omega(1)$ local read at all sites) |
| **Write Latency & Cost** | Low (Single node commit) | Moderate (Propagate to $K < N$ nodes) | High (Must update and sync $N$ nodes) |
| **System Availability** | Low (Node down = Fragment down) | Balanced fault tolerance | High ($N-1$ node failures tolerated) |
| **Consistency Overhead**| None (Zero replica divergence) | Moderate (Enforce quorum or sync) | Maximum (Continuous global consensus) |
