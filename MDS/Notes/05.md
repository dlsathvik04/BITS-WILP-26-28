## 3. Key Concepts & Formal Definitions

| Concept / Term | Formal Definition & Operational Meaning | Contextual Constraints / Properties |
| :--- | :--- | :--- |
| **Distributed Database** | A collection of multiple logically interrelated databases physically stored across different sites over a computer network[cite: 1]. | Physical distribution alone is insufficient; data must retain logical coherence and organizational relation[cite: 1]. |
| **DDBMS** | Distributed Database Management System; the collection of software programs managing distributed databases transparently[cite: 1]. | Provides communication, coordination, transaction management, and execution optimization across nodes[cite: 1]. |
| **Distribution Transparency** | An abstraction property ensuring users formulate queries against a single global database schema without awareness of physical data layout[cite: 1]. | Hides data locations, network fragmentation, and replication schemes from programmers and end users[cite: 1]. |
| **Local Autonomy** | The capability of an individual node to manage its local data and execute local operations independently without mandatory network coordination[cite: 1]. | Minimizes network latency; critical for maintaining site performance during wide-area operations[cite: 1]. |
| **Horizontal Fragmentation** | Partitioning a relation into subsets of complete tuples (rows) based on specific qualification predicates[cite: 1]. | Reconstructible via the Set Union ($\cup$) operator across all horizontal fragments[cite: 1]. |
| **Derived Horizontal Fragmentation** | Partitioning a relation based on the horizontal fragmentation scheme of another related relation via a foreign key relationship[cite: 1]. | Requires an equi-join condition between the related tables on the shared attribute key[cite: 1]. |
| **Vertical Fragmentation** | Decomposing a relation into subsets of attributes (columns) based on query access affinity[cite: 1]. | Must retain the primary key in every fragment to permit lossless reconstruction via Equi-Join ($\bowtie$)[cite: 1]. |
| **Union Compatibility** | A formal algebraic constraint requiring two relations to possess an identical number of attributes with matching corresponding domains[cite: 1]. | Invariant requirement for applying the Set Union ($\cup$) operator during reconstruction[cite: 1]. |
| **Quorum Consensus** | A mathematical voting mechanism in leaderless systems where read and write operations require confirmation from defined subsets of nodes[cite: 1]. | Invariant: $w + r > N$, ensuring at least one overlapping node holds the most recent update[cite: 1]. |

## 4. Detailed Structured Technical Lecture Notes

### I. Foundations of Distributed Database Systems

#### Overview & Theoretical Foundation
Traditional database designs rely on a single centralized server processing queries from multiple client applications[cite: 1]. As modern enterprises become geographically dispersed, maintaining a centralized database model introduces critical operational liabilities, most notably single points of failure (SPOF) and wide-area network latency[cite: 1]. A Distributed Database System mitigates these challenges by physically distributing data across multiple processing nodes (sites) interconnected via a computer network while maintaining a single, logically unified data environment[cite: 1]. This design improves availability and system reliability, as the crash of a single site allows the remaining $N - 1$ sites to continue operational execution[cite: 1].

#### Mechanics & Operational Invariants
1. **Locality of Reference:** Data is partitioned and placed physically proximate to the geographic location where it is most frequently queried (e.g., Delhi operational records stored locally on the Delhi site)[cite: 1]. This reduces wide-area data transmission costs and optimizes response time[cite: 1].
2. **Horizontal vs. Vertical Scalability:**
   * Centralized servers rely on vertical scaling (scaling up), wherein a server's processing capacity is expanded sequentially ($X \to 2X \to 4X$) by augmenting onboard RAM, CPU, and physical storage hardware within a single box[cite: 1].
   * Distributed systems implement horizontal scaling (scaling out), incrementally increasing cumulative compute and storage by adding discrete, modular network nodes without requiring existing sites to halt operation[cite: 1].
3. **Execution Separation:** 
   * **Local Transactions:** The transaction accesses and modifies data solely situated at the submitting site, terminating without inter-site coordination[cite: 1].
   * **Global Transactions:** The transaction accesses data dispersed across multiple sites, necessitating multi-node coordination and distributed sub-query execution[cite: 1].

```
+-------------------------------------------------------------+
|              Global Application / Programmer                |
+-------------------------------------------------------------+
                              | Submits Global Query
                              v
+-------------------------------------------------------------+
|         Distributed DBMS Layer (Abstract Coordinator)       |
+-------------------------------------------------------------+
          |                         |                        |
          v Network                 v Network                v Network
+-------------------+     +-------------------+     +-------------------+
|      Site 1       |     |      Site 2       |     |      Site 3       |
|  [Local DBMS]     |     |  [Local DBMS]     |     |  [Local DBMS]     |
|  [Local Database] |     |  [Local Database] |     |  [Local Database] |
+-------------------+     +-------------------+     +-------------------+
```

#### Complexity & Algorithmic Analysis
| Metric | Bound | Derivation / Justification from Lecture |
| :--- | :--- | :--- |
| **Best-Case Latency** | $\Omega(1)$ local operations | Queries satisfied entirely by the local partition execute against local DBMS engines with zero network round-trip delays[cite: 1]. |
| **Worst-Case Latency** | $O(k)$ network hops | Global queries requiring access to $k$ distributed remote sites incur round-trip network transport, serial wait states, and cross-site coordination overhead[cite: 1]. |
| **Failure Tolerance** | $\Theta(N - m)$ active nodes | If $m$ nodes fail in an $N$-node topology, the system retains partial operational availability over the remaining $N - m$ non-failed, non-replicated sites[cite: 1]. |
| **Storage Complexity** | $O(S)$ baseline footprint | Non-replicated distributed instances maintain a combined physical memory footprint equivalent to the baseline centralized database size $S$[cite: 1]. |

#### Design Trade-offs & Limitations
Distributed database models eliminate single-box compute bottlenecks and localize query workloads[cite: 1]. However, they introduce significant architectural overhead: network-induced transmission latency, complex multi-site failure recovery scenarios, and increased exposure to transmission line cutouts, which isolate healthy nodes from participating in global transactions[cite: 1].

### II. Architectural Classifications: Homogeneous, Heterogeneous, and Multi-Database Systems

#### Overview & Theoretical Foundation
Distributed database implementations vary based on the homogeneity of the underlying software, data structures, and administrative governance[cite: 1]. The complexity of query translation and global orchestration increases sharply as the system diverges from identical software stacks toward the integration of legacy, pre-existing database environments[cite: 1].

#### Mechanics & Operational Invariants
1. **Homogeneous Systems:** Every participating site utilizes the exact same database engine (e.g., all MySQL instances or all PostgreSQL instances) and identical data models (relational schema)[cite: 1]. Query commands dispatched by the global coordinator require no translation layer, as syntax, semantics, and primitive data representations are uniform across nodes[cite: 1].
2. **Heterogeneous Systems:** Participating nodes run disparate database software engines (e.g., Site 1 on MySQL, Site 2 on PostgreSQL, Site 3 on an enterprise database)[cite: 1]. 
   * The DDBMS layer maintains metadata describing the technology stack deployed at each site[cite: 1].
   * The DDBMS parses the unified global query and performs automated semantic and syntactic query transformation to generate native target queries compliant with the destination engine's grammar and schema types[cite: 1].
3. **Multi-Database Systems:** Systems constructed by federating pre-existing, fully autonomous databases (typically resulting from corporate mergers or acquisitions)[cite: 1]. 
   * Nodes refuse to relinquish independent operational control[cite: 1].
   * An integration layer orchestrates communication without displacing the underlying disparate database management software[cite: 1].

#### Complexity & Algorithmic Analysis
| Metric | Bound | Derivation / Justification from Lecture |
| :--- | :--- | :--- |
| **Homogeneous Query Translation** | $O(1)$ | No linguistic or structural schema transformations; direct dispatch of sub-queries[cite: 1]. |
| **Heterogeneous Query Translation** | $O(T)$ | Proportional to transformation cost $T$ per site, resolving data type casting, dialect variations, and schema divergence[cite: 1]. |
| **Federated Query Coordination** | $O(S_{auto})$ | Dominated by negotiations across autonomous systems ($S_{auto}$) enforcing independent security, locking, and access boundaries[cite: 1]. |
| **Schema Space Complexity** | $O(G + \sum L_i)$ | Requires maintaining the global integrated schema $G$ alongside local operational catalog metadata $L_i$ across all sites[cite: 1]. |

#### Design Trade-offs & Limitations
Homogeneous deployments provide optimal execution efficiency and simplified transaction management, but lock enterprises into a single software vendor[cite: 1]. Heterogeneous and multi-database topologies enable organizational autonomy and legacy preservation, but incur steep performance penalties due to translation pipelines and complex synchronization across diverse transaction models[cite: 1].

### III. Data Fragmentation Mechanics & Algebraic Reconstruction

#### Overview & Theoretical Foundation
Data partitioning (fragmentation) consists of breaking relational database objects into smaller, mathematically bounded subsets that are placed at distinct network nodes[cite: 1]. Fragmentation prevents queries from continuously scanning monolithic tables, significantly reducing execution times and communication costs[cite: 1]. Every valid fragmentation strategy must satisfy the strict reconstruction invariant: the original relational schema and instances must be losslessly reconstructible through relational algebra operators[cite: 1].

#### Mechanics & Operational Invariants

##### 1. Primary Horizontal Fragmentation
Divides a relation $R$ into subsets of tuples using the relational algebra selection operator ($\sigma$) governed by a qualification predicate[cite: 1]:
$$R_i = \sigma_{P_i}(R)$$
For instance, fragmenting an `Employee` relation by geographic placement:
$$\text{Emp}_{\text{Delhi}} = \sigma_{\text{Location} = '\text{Delhi}'}(\text{Employee})$$[cite: 1]
$$\text{Emp}_{\text{Mumbai}} = \sigma_{\text{Location} = '\text{Mumbai}'}(\text{Employee})$$[cite: 1]

* **Reconstruction Invariant (Set Union):** The base relation is reconstructed via the algebraic Union ($\cup$) operator across all disjoint horizontal fragments[cite: 1]:
  $$\text{Employee} = \text{Emp}_{\text{Delhi}} \cup \text{Emp}_{\text{Mumbai}}$$[cite: 1]
* **Union Compatibility Constraint:** The Set Union operator can only be applied between relations that possess the exact same arity (number of attributes) and identical attribute data type domains in corresponding positions[cite: 1].

##### 2. Derived Horizontal Fragmentation
Fragments a child relation based on the horizontal fragmentation criteria of an associated parent relation connected via a primary key/foreign key relationship[cite: 1].
* **Execution Procedure:**
  1. Horizontally partition the parent relation (e.g., `Department` partitioned by department number)[cite: 1]:
     $$\text{Dept}_4 = \sigma_{\text{Dnumber} = 4}(\text{Department})$$[cite: 1]
     $$\text{Dept}_5 = \sigma_{\text{Dnumber} = 5}(\text{Department})$$[cite: 1]
  2. Compute derived fragments of the dependent relation (`Employee`) using an Equi-Join ($\bowtie$) on the foreign key attribute[cite: 1]:
     $$\text{Emp}_{\text{Dept4}} = \text{Employee} \bowtie_{\text{Employee.Dnumber} = \text{Dept}_4\text{.Dnumber}} \text{Dept}_4$$[cite: 1]
     $$\text{Emp}_{\text{Dept5}} = \text{Employee} \bowtie_{\text{Employee.Dnumber} = \text{Dept}_5\text{.Dnumber}} \text{Dept}_5$$[cite: 1]
* **Boundary Case:** If an equi-join condition lacks matching parent keys, orphaned child tuples fail to map to any partition, violating the complete reconstruction requirement[cite: 1]. Natural joins ($\ast$) can automate this join if attribute naming remains completely identical across schemas[cite: 1].

##### 3. Vertical Fragmentation
Decomposes a relation $R$ into subsets of columns using the relational algebra projection operator ($\Pi$)[cite: 1]:
$$R_1 = \Pi_{\text{Attrs}_1}(R), \quad R_2 = \Pi_{\text{Attrs}_2}(R)$$[cite: 1]

* **Primary Key Preservation Invariant:** The relation's primary key must be intentionally duplicated across every vertical fragment[cite: 1]. Omitting the primary key breaks relational tuple identity, making lossless reconstruction algebraically impossible[cite: 1].
* **Reconstruction Invariant (Equi-Join):**
  $$\text{Employee} = R_1 \bowtie_{\text{Employee\_ID}} R_2$$[cite: 1]
  *(Union cannot be used here because vertical fragments contain different attribute sets and fail union compatibility)[cite: 1].*

##### 4. Mixed (Hybrid) Fragmentation
Applies horizontal and vertical partitioning recursively in alternating sequences (e.g., horizontal selection by region followed by vertical projection of payroll versus contact data)[cite: 1]. Reconstruction requires a multi-stage algebraic tree combining joins and unions[cite: 1].

#### Complexity & Algorithmic Analysis
| Metric | Bound | Derivation / Justification from Lecture |
| :--- | :--- | :--- |
| **Horizontal Scan Cost** | $\Theta\left(\frac{N_{\text{rows}}}{k}\right)$ | Selection against a horizontally fragmented table of $k$ partitions scans only local rows rather than the complete dataset[cite: 1]. |
| **Horizontal Reconstruction** | $O(\sum |R_i|)$ | Set union across disjoint partitions executes proportional to the cumulative record count without duplicate elimination costs[cite: 1]. |
| **Vertical Reconstruction** | $O(|R_1| \bowtie |R_2|)$ | Equi-join on primary key attribute requires matching indexes; complexity depends on join implementation[cite: 1]. |
| **Primary Key Space Overhead** | $O(m \cdot K)$ | For $m$ vertical fragments, primary key data of size $K$ must be stored redundantly $m-1$ additional times[cite: 1]. |

#### Design Trade-offs & Limitations
Horizontal fragmentation optimizes geographic locality and enables parallel writes across distinct nodes[cite: 1]. Vertical fragmentation isolates high-affinity attribute subsets (e.g., separating frequently accessed user profile data from infrequently queried payroll figures), which minimizes disk I/O[cite: 1, 1]. However, if application queries routinely require attributes or rows spanning multiple fragments, reconstruction operations incur high cross-site network joins and aggregation latencies[cite: 1].

### IV. Data Allocation and Replication Topologies

#### Overview & Theoretical Foundation
Following data fragmentation, the system must assign these database partitions to physical network sites (Data Allocation)[cite: 1]. The chosen allocation and replication topology dictates the trade-off boundaries between system availability, network read latency, write amplification, and cross-site consistency[cite: 1].

#### Mechanics & Operational Invariants

```
+-----------------------------------------------------------------------------+
|                          Data Allocation Strategies                         |
+-----------------------------------------------------------------------------+
         |                                     |                         |
         v                                     v                         v
+-----------------------+           +--------------------+     +--------------------+
|    Non-Replicated     |           | Partial Replicated |     |  Fully Replicated  |
|  1 Site per Fragment  |           | Selected Replicas  |     | All Sites Have All |
|  Min Storage / Writes |           | Balanced Trade-off |     | Max Availability   |
|  Lower Availability   |           +--------------------+     | Heavy Write Cost   |
+-----------------------+                                      +--------------------+
```

1. **Non-Replicated Allocation:**
   * Each fragment resides on exactly one physical site[cite: 1].
   * Zero redundant copies are stored across the network[cite: 1].
   * If a site goes offline, its assigned fragment becomes entirely unavailable until physical machine recovery completes[cite: 1].
2. **Fully Replicated Allocation:**
   * A full copy of the entire database exists across all participating sites[cite: 1].
   * Local read execution is available system-wide[cite: 1].
   * Every write/update operation must be propagated across all network sites, maximizing update overhead[cite: 1].
3. **Partially Replicated Allocation:**
   * High-priority or frequently accessed fragments are replicated to a selective subset of nodes[cite: 1].
   * Balances write amplification costs against system availability demands[cite: 1].

#### Replication Mechanics

```
SYNCHRONOUS REPLICATION
Client ----> Primary Node ----(Update)----> Secondary Node
                |                                  |
                | <-------(Ack Success)------------+
                v
       Confirm Success to Client

ASYNCHRONOUS REPLICATION
Client ----> Primary Node ----(Confirm Success to Client)
                |
           (Later Lag)
                |
                +---------(Update)--------> Secondary Node (Temporarily Stale)
```

1. **Synchronous Replication:**
   * The primary node propagates updates across all designated replicas before reporting execution success to the calling client[cite: 1].
   * Guarantees strong consistency; replicas never serve stale data[cite: 1].
   * Incurs high write latency and is fragile to slow or temporarily disconnected replicas[cite: 1].
2. **Asynchronous Replication:**
   * The primary node updates its local partition and immediately confirms completion to the client[cite: 1].
   * Propagation to secondary nodes occurs in the background[cite: 1].
   * Low write latency, but introduces replication lag where secondaries temporarily return stale data[cite: 1].

#### Replication Topologies
* **Single-Leader (Primary-Follower):** All write requests route to a single designated leader[cite: 1]. The leader applies changes locally and streams updates to follower nodes[cite: 1]. Read requests are served by either the leader or followers to scale read throughput[cite: 1]. If the primary fails, a consensus protocol must elect a new leader among surviving followers[cite: 1].
* **Multi-Leader:** Multiple regional leader nodes accept writes simultaneously (e.g., Delhi leader processes Delhi writes, Mumbai leader processes Mumbai writes)[cite: 1]. Leaders apply changes locally and replicate them to other regional leaders asynchronously[cite: 1].
  * *Write-Conflict Boundary:* If Leader A changes variable $X$ from $50 \to 100$ while Leader B changes $X$ from $50 \to 200$ concurrently, both accept valid local writes[cite: 1]. Reconciling these states requires conflict resolution protocols (such as timestamp ordering) during cross-leader synchronization[cite: 1].
* **Leaderless (Quorum Consensus):** No coordinator or master node exists[cite: 1]. Clients dispatch writes and reads directly to multiple replicas simultaneously[cite: 1].
  * Let $N$ represent the total number of replica nodes, $w$ represent the write quorum size, and $r$ represent the read quorum size[cite: 1].
  * **The Quorum Condition:**
    $$w + r > N$$[cite: 1]
  * **Strict Majority Proof Example ($N=9$):**
    Taking the ceiling of half the nodes:
    $$\left\lceil \frac{9}{2} \right\rceil = 5$$[cite: 1]
    Assigning $w = 5$ and $r = 5$:
    $$w + r = 5 + 5 = 10 > 9$$[cite: 1]
    Because the sum strictly exceeds total nodes $N$, any read set of 5 nodes must overlap with at least one node from the write set of 5 nodes[cite: 1]. This guarantees that at least one responding node holds the latest write timestamp, ensuring data freshness despite lacking a centralized leader[cite: 1].

#### Complexity & Algorithmic Analysis
| Metric | Bound | Derivation / Justification from Lecture |
| :--- | :--- | :--- |
| **Fully Replicated Storage** | $\Theta(N \cdot S)$ | Replicating database size $S$ across $N$ sites linearly multiplies total hardware disk consumption[cite: 1]. |
| **Synchronous Write Latency** | $O(\max(t_1, t_2, \dots, t_R))$ | Write completion latency is bounded by the slowest responding replica over the wide-area network[cite: 1]. |
| **Asynchronous Write Latency** | $O(t_{\text{local}})$ | Update returns immediately following local primary disk commit, ignoring network propagation lag[cite: 1]. |
| **Quorum Verification Time** | $O(\max(t_{w1 \dots wk}))$ | Leaderless updates require waiting for confirmations from the $w$-th fastest replica[cite: 1]. |

#### Design Trade-offs & Limitations
Single-leader systems avoid write conflicts but establish a localized bottleneck for global writes[cite: 1]. Multi-leader topologies improve write latency across geographic regions but introduce write conflicts that must be resolved through timestamping or convergence logic[cite: 1]. Leaderless quorum setups provide high fault tolerance without failover delays, but require quorum overlapping rules ($w + r > N$) and multi-node read checks to detect and resolve stale data[cite: 1].
