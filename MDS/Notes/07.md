## 3. Key Concepts & Formal Definitions

| Concept / Term | Formal Definition & Operational Meaning | Contextual Constraints / Properties |
| :--- | :--- | :--- |
| **NoSQL** | "Not Only SQL"; database architectures designed to complement SQL with flexible data models, horizontal scalability, and distributed processing. | Does not eliminate SQL; emphasizes schema flexibility and lack of costly multi-node relational joins. |
| **Fixed vs. Flexible Schema** | Fixed schema requires every record to conform to uniform columnar structures; flexible schema permits heterogeneous attributes across entries. | Schema modifications in fixed schemas require expensive migrations; flexible schemas adapt dynamically at runtime. |
| **Key-Value Store** | A storage model associating an arbitrary, opaque data payload (value) with a unique addressing identifier (key). | Values are accessed via direct key lookups; the internal payload is treated as a single entity without server-side property indexing. |
| **Column-Family Store** | A database architecture grouping related column subsets that are frequently queried together into contiguous physical storage units. | Values of a column family are laid out adjacently on disk/memory; avoids scanning non-relevant columns during row traversals. |
| **Graph Database** | A database model representing entities as nodes and relationships as edges with direct pointer/structural traversal. | Ideal for highly connected networks (social graphs, recommendation engines, fraud detection); queries utilize Cypher. |
| **Redis Sentinel** | A dedicated monitoring service that tracks the health of Redis primary and secondary nodes. | Detects node failures automatically and orchestrates leader election / automatic failover of a secondary replica to primary status. |
| **RDB (Redis Database Snapshot)** | A persistence mechanism creating periodic point-in-time binary images of dataset state saved to disk. | Compact representation suited for backup/recovery; data modifications executed after the last snapshot are lost upon sudden crash. |
| **AOF (Append-Only File)** | A persistence mechanism logging every sequential write/update operation executed against the dataset. | High write durability; logs can be replayed sequentially on startup to reconstruct data, trading off performance for safety. |
| **TTL (Time-To-Live)** | A configurable lifespan assigned to an in-memory key after which the engine automatically purges it. | Key expiration counter evaluated in seconds; returns positive integer for remaining life, `-1` if persistent, and `-2` or `nil` if expired/non-existent. |

## 4. Detailed Structured Technical Lecture Notes

### I. Architectural Limitations of Relational Databases in Modern Computing

#### Overview & Theoretical Foundation
Relational Database Management Systems (RDBMS) have anchored enterprise software architecture for over three decades since the 1970s. While highly successful for structured data with strong transactional (ACID) guarantees, traditional RDBMS architectures face steep performance bottlenecks under modern web-scale application demands. 

Modern workloads are defined by the Three Vs of Big Data:
1. **Volume:** Exponential growth in data volume requiring multi-server capacity beyond vertical scaling boundaries.
2. **Variety:** Diversification of data formats where an estimated 80% of enterprise data is unstructured (audio, video, raw text), 10% is semi-structured (JSON, XML), and only 10% is strictly structured.
3. **Velocity:** Ingestion streams requiring real-time updates and continuous access latencies.

Under the CAP Theorem, traditional relational systems prioritize Consistency ($C$) and Availability ($A$) in centralized topologies ($CA$). When deployed across geographically distributed sites, network partitions ($P$) force systems to coordinate state over high-latency networks. A distributed join requires moving large relational tables across network links, inducing catastrophic latency penalties and potential availability failures during link disruptions.

#### Mechanics & Operational Invariants
* **Vertical vs. Horizontal Scalability:** RDBMS systems scale vertically (replacing a node with higher-tier compute/memory), requiring planned server downtimes and reaching hardware cost and architectural limits. Modern workloads demand horizontal scale-out (adding commodity nodes to an active cluster), linearly increasing compute and storage capacity without downtime.
* **Schema Evolution Bottlenecks:** Predefined, rigid tabular structures force repeated ALTER TABLE executions and migration pipelines when business requirements alter entity models. Modern architectures require runtime schema evolution where records within the same conceptual container hold diverse schemas.
* **Denormalization Workloads:** While normalization eliminates redundancy, read-intensive analytical workflows suffer due to multi-table joins. As data scales, applications intentionally denormalize structures into contiguous formats to preserve read efficiency.

### II. Taxonomy of NoSQL Storage Architectures

#### Overview & Theoretical Foundation
NoSQL systems depart from standard relational models by employing heterogeneous data representations tailored for specialized query patterns, horizontal distribution, and configurable consistency (ranging from strict ACID to BASE / Eventual Consistency).

```
                 +--------------------------------+
                 |    NoSQL Storage Paradigms     |
                 +---------------+----------------+
                                 |
        +----------------+-------+--------+---------------+
        |                |                |               |
+-------v-------+ +------v------+ +-------v------+ +------v-------+
|  Key-Value    | |  Document   | |Column-Family | |    Graph     |
| (Redis/Dynamo)| |(MongoDB/BSON| | (Cassandra/  | |(Neo4j/Amazon |
| Opaque Values | | Nested Tree | |    HBase)    | |   Neptune)   |
+---------------+ +-------------+ +--------------+ +--------------+
```

#### Detailed Taxonomy Breakdown
1. **Key-Value Stores (e.g., Redis, AWS DynamoDB, Riak):**
   * The simplest paradigm. Pairs an opaque data blob with a unique addressing key via hash indexing.
   * Optimized strictly for known-key retrievals, caching layers, real-time counters, and session tracking.
2. **Document Databases (e.g., MongoDB, Couchbase):**
   * Organizes data into self-describing, hierarchical documents (JSON, BSON, XML) encapsulated within *Collections* (analogous to tables).
   * Supports nested attributes and schema polymorphism, allowing documents within the same collection to maintain distinct attribute fields.
3. **Column-Family Databases (e.g., Apache Cassandra, Apache HBase):**
   * Stores data row-by-row, but groups related attributes into discrete, contiguous columnar storage partitions called *Column Families*.
   * Prevents total-row I/O overhead: queries targeting attributes $A_1 \dots A_5$ read exclusively from Column Family 1, ignoring $A_6 \dots A_{10}$.
4. **Graph Databases (e.g., Neo4j, Amazon Neptune):**
   * Expresses domain topology natively as *Nodes* (entities) and *Edges* (directed/undirected relationships).
   * Eliminates join overhead in connection-heavy datasets (social networks, recommendation engines, fraud rings) using specialized traversal query languages (e.g., Cypher).

### III. Key-Value Architecture & Storage Internals

#### Overview & Theoretical Foundation
Key-value systems model storage as a distributed associative map (hash table/dictionary). The underlying engine maps an application-level key to a physical memory address or storage node using an internal hash function. Values are treated by the core storage engine as opaque single entities; sub-properties within complex JSON or nested objects cannot be queried or updated server-side without retrieving or re-writing the complete entity payload.

#### Mechanics & Operational Invariants
1. **Distributed Hashing & Addressing:** Keys are processed via internal hash functions (e.g., $h(\text{key}) \pmod M$) to resolve memory indexes across partitioned cluster instances.
2. **Read/Write Operations:**
   * `SET / PUT key value`: Generates the hash digest of the key and maps the pointer directly to the contiguous allocated block containing `value`.
   * `GET key`: Evaluates the hash function and performs an immediate dereference to read out the complete payload.
   * `DEL key`: Unlinks the key from the hash registry and deallocates memory.
3. **Master-Replica Distribution:**
   * All mutations (writes/updates) route directly to the designated Primary node.
   * The Primary replicates write streams asynchronously or synchronously to Secondary replica nodes.
   * Reads can be distributed across Secondary replicas to scale read throughput and ensure high availability.
   * Redis Sentinel monitors heartbeat pings; if the Primary becomes unreachable, Sentinel promotes an elected Secondary to Primary status using leader election protocols.

#### Complexity & Algorithmic Analysis
| Metric | Bound | Derivation / Justification from Lecture |
| :--- | :--- | :--- |
| **Best-Case Time** | $\Omega(1)$ | Direct memory dereferencing through a pre-calculated hash function. |
| **Worst-Case Time** | $O(n)$ | Pathological hash collisions or cluster-wide blocking operations (e.g., production abuse of `KEYS *`). |
| **Average-Case Time** | $\Theta(1)$ | Stated lecture premise: fundamental design goal of hashing is constant-time lookups. |
| **Space Complexity** | $O(K + V)$ | Proportional to the size of stored keys plus total aggregated payload value buffers. |

#### Design Trade-offs & Limitations
* **Lookups by Key Only:** Highly performant when the primary key is known, but incapable of native multi-attribute secondary indexing, range scans, or predicate filtering on value attributes.
* **Absence of Server-Side Joins:** If data entities share relationships, joining requires manual, application-tier orchestration across multiple `GET` operations.

### IV. Redis In-Memory Engine, Persistence, and Data Structures

#### Overview & Theoretical Foundation
Redis (Remote Dictionary Server) is an open-source, in-memory key-value data structure store utilized primarily for ultra-low-latency operations, caching, and real-time state manipulation. Because data resides in volatile RAM, Redis implements optional disk-persistence models (RDB and AOF) to provide durability across server restarts.

#### Data Structures Supported
* **Strings:** Fundamental byte arrays capable of holding text, serialized JSON, binary blobs, or numeric values up to system limits.
* **Hashes:** Field-value maps representing structured objects (e.g., student/user profiles) beneath a single top-level key namespace.
* **Lists:** Ordered sequences of string elements implemented as linked nodes/lists, optimal for FIFO/LIFO pipelines, queueing, and activity logs.
* **Sets:** Unordered collections of unique strings that automatically discard duplicate insertions.
* **Sorted Sets (ZSets):** Non-repeating string collections where each member is coupled to a floating-point numeric score, maintaining strict element ordering for leaderboards and ranking engines.

#### Mechanics: Persistence Engines
1. **RDB (Snapshotting):** Periodic point-in-time dumps to a compact binary file. Highly efficient for cold storage, replication, and disaster recovery. However, operations occurring between the last snapshot and a crash are lost.
2. **AOF (Append-Only File):** A write-ahead sequential logging mechanism recording every mutating command (`SET`, `DEL`). Guarantees high durability; on restart, the engine replays the AOF log to reconstruct state.

```
+---------------+     Write Op      +---------------+     Log Append    +---------------+
|  Client Write | ----------------> | In-Memory RAM | ----------------> | AOF Log Disk  |
+---------------+                   +---------------+                   +---------------+
                                            |
                                            | Periodic Snapshot
                                            v
                                    +---------------+
                                    | RDB Disk Dump |
                                    +---------------+
```

### V. Redis CLI Command Reference & Execution Mechanics

All Redis operations are executed within the `redis-cli` interactive console. Redis keys are case-sensitive.

#### 1. String & Basic Key-Value Commands
* **`SET key value`**: Writes or overwrites a key with a designated value.
  ```text
  127.0.0.1:6379> SET name Ashish
  OK
  ```
* **`GET key`**: Retrieves the value mapped to the key; returns `nil` if missing.
  ```text
  127.0.0.1:6379> GET name
  "Ashish"
  ```
* **`SETNX key value`** (*Set if Not eXists*): Atomic insertion. Sets the key only if it does not already exist. Returns `1` on success, `0` if the key exists (preventing overwrite).
  ```text
  127.0.0.1:6379> SETNX xyz 101
  (integer) 1
  127.0.0.1:6379> SETNX xyz 202
  (integer) 0
  ```
* **`MSET key1 val1 key2 val2 ...`**: Atomically creates multiple key-value pairs.
  ```text
  127.0.0.1:6379> MSET course "Modern Database Systems" faculty Ashish sem "July 26th"
  OK
  ```
* **`MGET key1 key2 ...`**: Retrieves an ordered list of values for multiple keys.
  ```text
  127.0.0.1:6379> MGET course faculty sem
  1) "Modern Database Systems"
  2) "Ashish"
  3) "July 26th"
  ```
* **`APPEND key value`**: Concatenates a string suffix to an existing key's value.
  ```text
  127.0.0.1:6379> SET city New
  OK
  127.0.0.1:6379> APPEND city Delhi
  (integer) 8
  127.0.0.1:6379> GET city
  "NewDelhi"
  ```
* **`STRLEN key`**: Returns the integer byte length of the stored string.
  ```text
  127.0.0.1:6379> STRLEN city
  (integer) 8
  ```
* **`EXISTS key`**: Checks for the existence of a key. Returns `1` (true) or `0` (false).
  ```text
  127.0.0.1:6379> EXISTS city
  (integer) 1
  ```
* **`DEL key`**: Explicitly unlinks and removes a key-value record.
  ```text
  127.0.0.1:6379> DEL city
  (integer) 1
  ```
* **`TYPE key`**: Returns the internal data structure type mapped to the key (`string`, `hash`, `list`, `set`, `zset`).
  ```text
  127.0.0.1:6379> TYPE name
  string
  ```
* **`KEYS pattern`**: Scans keyspace for matching patterns (e.g., `KEYS *`).  
  *Operational Precaution:* `KEYS *` blocks execution on single-threaded Redis engines; prohibited in production environments containing high volumes of keys.

#### 2. Atomic Numeric Counters
* **`INCR key`**: Increments an integer string value by 1.
  ```text
  127.0.0.1:6379> SET visitors 200
  OK
  127.0.0.1:6379> INCR visitors
  (integer) 201
  ```
* **`INCRBY key increment`**: Increments the integer value by a specified step size.
  ```text
  127.0.0.1:6379> INCRBY visitors 30
  (integer) 231
  ```
* **`DECR key`**: Decrements the integer value by 1.
  ```text
  127.0.0.1:6379> DECR visitors
  (integer) 230
  ```

#### 3. Key Expiration & Volatility Management
* **`SET key value EX seconds`**: Sets a key with an embedded time-to-live expiration.
  ```text
  127.0.0.1:6379> SET otp 123456 EX 20
  OK
  ```
* **`TTL key`**: Returns the remaining active lifetime in seconds:
  * Returns $>0$: Seconds remaining.
  * Returns `-1`: Key exists indefinitely (no TTL attached).
  * Returns `-2`: Key has expired or does not exist.
  ```text
  127.0.0.1:6379> TTL otp
  (integer) 14
  ```
* **`PERSIST key`**: Clears the expiration timer from a volatile key, converting it back into a permanent in-memory record.
  ```text
  127.0.0.1:6379> PERSIST otp
  (integer) 1
  127.0.0.1:6379> TTL otp
  (integer) -1
  ```

#### 4. Hash Set (HSET) Record Operations
* **`HSET key field1 val1 field2 val2 ...`**: Associates multiple field-value pairs under a parent hash key.
  ```text
  127.0.0.1:6379> HSET student:101 name Ashish age 32 department CSIS
  (integer) 3
  ```
* **`HGET key field`**: Reads a singular field attribute within a hash.
  ```text
  127.0.0.1:6379> HGET student:101 age
  "32"
  ```
* **`HMGET key field1 field2 ...`**: Retrieves multiple field values from a hash in a single round-trip.
  ```text
  127.0.0.1:6379> HMGET student:101 name department
  1) "Ashish"
  2) "CSIS"
  ```
* **`HGETALL key`**: Returns all field labels and values stored under the hash.
  ```text
  127.0.0.1:6379> HGETALL student:101
  1) "name"
  2) "Ashish"
  3) "age"
  4) "32"
  5) "department"
  6) "CSIS"
  ```
* **`HKEYS key`**: Extracts an array of field names from a designated hash.
  ```text
  127.0.0.1:6379> HKEYS student:101
  1) "name"
  2) "age"
  3) "department"
  ```
* **`HVALS key`**: Extracts an array of all values from a designated hash.
  ```text
  127.0.0.1:6379> HVALS student:101
  1) "Ashish"
  2) "32"
  3) "CSIS"
  ```
* **`HLEN key`**: Returns the total number of distinct fields stored inside the hash set.
  ```text
  127.0.0.1:6379> HLEN student:101
  (integer) 3
  ```
