## 3. Key Concepts & Formal Definitions

| Concept / Term | Formal Definition & Operational Meaning | Contextual Constraints / Properties |
| :--- | :--- | :--- |
| **Distributed Transaction** | A logical unit of work whose constituent database operations execute across two or more geographically distributed physical sites. | Must satisfy ACID properties globally; sub-transactions must either commit collectively or abort collectively without partial commits. |
| **Global Transaction Manager (GTM)** | The coordinator node—typically the site where a transaction or query is initially submitted—responsible for orchestrating global decisions. | Dynamically assigned per transaction; manages the execution state of participating nodes. |
| **Local Transaction Manager (LTM)** | The local software module at an individual participating site that executes its allocated sub-transaction and maintains local concurrency control and recovery. | Behaves like an autonomous centralized DBMS engine for its local data slice. |
| **Consistency (CAP)** | The guarantee that every read operation executed on any replica node returns the exact same, most up-to-date data value across the cluster. | A read request must never return stale data; if replicas are not synchronously updated, the system is inconsistent. |
| **Availability (CAP)** | The requirement that every non-failing node receiving a read or write request must return a non-error response (success or failure) within a bounded, reasonable timeframe. | Unresponsiveness or client timeout constitutes an availability failure; explicit operational errors (such as transaction aborts) maintain availability. |
| **Partition Tolerance (CAP)** | The capacity of a distributed system to continue processing operations despite network partitions that interrupt communication links between nodes. | Fundamental invariant in distributed environments; communication failures across commodity hardware are inevitable. |
| **Quorum Consensus** | A voting mechanism requiring a majority of replica nodes ($N/2 + 1$ out of $N$ nodes) to agree before declaring a read or write operation successful. | Eliminates split-brain anomalies and stale reads by ensuring that read sets and write sets always overlap by at least one node. |
| **Eventual Consistency** | A consistency model wherein replicas are permitted to temporarily diverge (soft state) following a write, with the guarantee that all replicas will converge to the identical state in the absence of further writes. | Foundational to AP and BASE distributed architectures (e.g., social timelines, recommendation systems). |

## 4. Detailed Structured Technical Lecture Notes

### I. Foundations of Distributed Data Management

#### Overview & Theoretical Foundation
Centralized database engines consolidate transactional state, concurrency control, and buffer management onto a single machine. While this simplifies transaction isolation and recovery, modern large-scale workloads encounter physical compute, storage, and network saturation limits. Distributed Database Management Systems (DDBMS) address these boundaries by distributing tables across an arbitrary number of interconnected nodes. Rather than requiring expensive, specialized hardware, distributed database clusters are typically constructed on top of commodity hardware—ranging from standard data centre machines to cloud-hosted virtual instances. 

Because nodes are geographically separated and linked via wide-area networks (WANs) or local cloud availability zones (such as AWS Regions and Availability Zones), distributed systems must balance the physical locality of data against communication overhead. Data is fragmented to place records near the geographical or organizational locus of access, minimizing message traversal over communication networks.

#### Mechanics & Operational Invariants
Data distribution relies on two fundamental partitioning models, accompanied by configurable allocation and replication strategies:

```
                          Original Relation
                                  |
         +------------------------+------------------------+
         |                                                 |
[Horizontal Partitioning]                         [Vertical Partitioning]
Tuples partitioned by predicate                   Attributes partitioned by schema
(e.g., City = 'Delhi' vs. 'Mumbai')               (e.g., {A1..A7} vs. {A8..A20})
         |                                                 |
         +------------------------+------------------------+
                                  |
                     [Hybrid / Derived Partitioning]
                     Horizontal on Vertical or Derived
                     via Semijoin / Foreign Key
```

1. **Partitioning Methodologies:**
   * **Horizontal Partitioning:** Subdivides a relation into disjoint subsets of tuples based on attribute values (predicates). For example, a relation with 10,000 tuples may partition into 4,000 records allocated to Site 1 and 6,000 records allocated to Site 2 based on geographical attributes.
   * **Vertical Partitioning:** Decomposes a relation by subsets of attributes (columns) that are frequently queried together. If a relation contains 20 attributes where columns $A_1$ through $A_7$ sustain high co-access, they are placed in a distinct sub-schema, while attributes $A_8$ through $A_{20}$ reside elsewhere. Primary keys are retained across fragments to permit reconstruction.
   * **Derived Horizontal Partitioning:** Partitions a child table based on the horizontal fragmentation criteria of an associated parent table, typically evaluated through join/foreign key relationships.
   * **Hybrid (Mixed) Partitioning:** Successive combinations of horizontal followed by vertical partitioning, or vice versa, tailored to complex application query profiles.
2. **Replication Topologies & Allocation:**
   * **Non-Replicated:** Each fragment exists at exactly one site. A failure of that site renders its constituent data completely unreachable.
   * **Fully Replicated:** Every physical node holds a full replica of every fragment. Read performance scales linearly with node count, but write operations incur maximum synchronization latency and network overhead.
   * **Partially Replicated:** Selected fragments are copied across a subset of sites based on localized operational frequency. Big data frameworks generally configure a default replication factor of 3, expanding to 4 or 5 for mission-critical reliability, or reducing to 1 or 2 for ephemeral datasets.
3. **Replication Coordination Schemes:**
   * **Leader-Follower (Primary-Secondary):** A designated leader node coordinates all write mutations, commits locally, and propagates changes to followers. Read requests can be routed to followers to offload the primary node.
   * **Multi-Leader:** Dedicated regional leaders coordinate writes within local geographies (e.g., Delhi and Mumbai), asynchronously reconciling updates across regions to prevent cross-continental write latency.
   * **Leaderless (Quorum-Based):** Clients broadcast write and read commands directly to $N$ replicas. A write is registered as successful only when an acknowledgment quorum $W$ is obtained:
     $$W \ge \left\lfloor \frac{N}{2} \right\rfloor + 1$$
     Similarly, a read quorum $R$ must read from $\lfloor N/2 \rfloor + 1$ nodes. For an odd cluster of $N = 9$ nodes, $W = 5$ and $R = 5$. Because $W + R > N$, any read quorum intersects a write quorum by at least one node:
     $$\{ \text{Nodes with write update} \} \cap \{ \text{Nodes selected for read} \} \ge 1$$
     If a read reveals differing values (e.g., 4 nodes returning stale data and 1 returning the updated value), the system identifies the mismatch and resolves the conflict.

### II. Distributed Transactions & Two-Phase Commit (2PC)

#### Overview & Theoretical Foundation
A distributed transaction consists of multiple database actions executed across distinct physical network sites that must execute under strict ACID semantics. Consider a funds transfer of 10,000 rupees: Account $A$ at the Delhi site must be debited by 10,000, and Account $B$ at the Mumbai site must be credited by 10,000. While the client treats this as a single logical transaction, it physically decomposes into two autonomous local sub-transactions. 

If Delhi successfully commits the debit while Mumbai aborts the credit due to a system crash or concurrency violation, the system violates the fundamental property of **Atomicity** ($A$ in ACID). The database enters an inconsistent partial state where money is destroyed. Distributed transaction management prevents this state by introducing coordination protocols that force all participating sites to reach an identical final commit or abort verdict.

#### Mechanics & Operational Invariants

```
Coordinator (GTM)                      Participant 1 (LTM)         Participant 2 (LTM)
      |                                        |                           |
      |=========== 1. PREPARE ================>|                           |
      |=========== 1. PREPARE ============================================>|
      |                                        |                           |
      |<---------- VOTE: YES ------------------|                           |
      |<---------- VOTE: YES (or NO) --------------------------------------|
      |                                        |                           |
[Determines Global Decision]                   |                           |
      |                                        |                           |
      |=========== 2. GLOBAL COMMIT (or ABORT)>|                           |
      |=========== 2. GLOBAL COMMIT (or ABORT)============================>|
      |                                        |                           |
      |<---------- ACK ------------------------|                           |
      |<---------- ACK ----------------------------------------------------|
```

1. **Architecture & Roles:**
   * **Global Transaction Coordinator (GTM):** The node receiving the client request acts as the coordinator for that transaction. Coordinator status rotates dynamically on a per-transaction basis (e.g., Delhi coordinates a transaction submitted at Delhi; Kolkata coordinates a transaction submitted at Kolkata).
   * **Participating Sites & Local Transaction Managers (LTM):** Nodes hosting fragments targeted by the transaction. Each LTM manages local concurrency control (locks), buffer writes, and local recovery logs.
2. **Two-Phase Commit Protocol Execution:**
   * **Phase 1: Voting / Prepare Phase:**
     * Following local sub-transaction execution, the GTM transmits a `PREPARE` command to all participating sites.
     * Each participant assesses its local state. It verifies that data locks are secured, execution constraints are satisfied, and all redo/undo log entries are safely written to non-volatile storage.
     * Participants respond with `VOTE: YES` if ready to guarantee a commit, or `VOTE: NO` if any internal error, concurrency failure, or local abort occurs.
   * **Phase 2: Decision / Commit Phase:**
     * **Universal Consensus (`VOTE: YES` from all):** The coordinator writes a commit record to its log and broadcasts `GLOBAL COMMIT`. Each LTM permanently applies changes, releases locked resources, and returns an acknowledgment.
     * **Veto or Failure (`VOTE: NO` from any participant):** If even one node votes `NO`, the coordinator issues `GLOBAL ABORT`. All participants roll back uncommitted changes to their prior stable state and release resources.
   * **Timeout Handling:** If a participant crashes or network disconnectivity prevents an acknowledgment, the coordinator waits for a predefined timeout threshold. If no response arrives, the coordinator presumes node failure and triggers a `GLOBAL ABORT`.

#### Design Trade-offs & Limitations
* **The Blocking Problem:** 2PC is a blocking protocol. If a participant votes `YES`, it relinquishes the unilateral right to abort or commit; it enters a prepared state, holding local locks. If the coordinator crashes before broadcasting the final decision, participants must wait indefinitely until the coordinator recovers to discover the outcome, keeping database locks active and causing cascading stalls.
* **Single Point of Dependency:** The coordinator manages the global consensus vector. A coordinator failure stalls completion of inflight transactions and demands recovery log analysis before downstream participants can proceed.
* **Communication Latency:** 2PC requires multiple sequential round-trip messages across wide-area networks (`PREPARE`, `VOTE`, `COMMIT/ABORT`, `ACK`). If a transaction spans 10 nodes across multiple data centres, cumulative network latency significantly degrades throughput compared to a local centralized engine.

### III. Distributed Query Processing & Optimization

#### Overview & Theoretical Foundation
Distributed query processing addresses declarative SQL statements whose underlying data tables reside on geographically disparate nodes. The core responsibility of the distributed query optimizer is to transform a global declarative query into an optimal distributed physical query execution plan. 

Because transferring data across network interfaces is orders of magnitude slower than local disk or memory operations, the primary cost objective of distributed query optimization differs from centralized systems:

$$\text{Total Cost} = \text{Data Transfer Volume} + \text{Network Communication Delay} + \text{Local Compute Processing Time}$$

The foundational design rule governing distributed execution is to **move computation closer to data**, rather than moving raw data to the point of computation.

#### Mechanics & Operational Invariants
1. **Query Processing Lifecycle:**
   * **Query Decomposition:** The coordinator decomposes a global SQL query into modular sub-queries corresponding to the relational operators ($\sigma, \pi, \bowtie$).
   * **Data Localization:** The optimizer inspects system catalogs to map tables, partitions, and fragments to specific physical cluster nodes.
   * **Local Execution:** Sub-queries execute natively via the storage engine of the target nodes.
   * **Result Integration:** Intermediate data sets are routed across the network to an integration node to finalize the global result (e.g., executing a final join or aggregation) before presenting it to the client.
2. **Relational Algebra Transformations for Cost Reduction:**
   * **Early Filtering (Selection, $\sigma$):** Push selections down to local nodes prior to data shipping. Given a query joining `Customer` ($10,000$ rows at Node 1) and `Orders` ($100,000$ rows at Node 2):
     * If the query contains a predicate `City = 'Delhi'`, filtering `Customer` locally reduces the candidate set from $10,000$ rows to $500$ rows.
     * If an order predicate `Amount > 5000` is present, filtering `Orders` locally reduces the volume from $100,000$ rows to $2,000$ rows.
   * **Early Projection ($\pi$):** Strip unneeded relation attributes locally before transmission. If `Orders` contains 20 attributes, but the final output and join require only `CustomerID` and `Amount`, project out the remaining 18 attributes locally, transferring only the two necessary columns across the network.
3. **Join Site Selection Strategies:**
   * **Data Shipping (Full Transfer):** Moving the entire `Orders` relation to Node 1, or moving `Customer` to Node 2. The optimizer computes transmission cost based on size: if `Customer` represents $1\text{ MB}$ and `Orders` represents $1\text{ GB}$, the optimal decision ships the $1\text{ MB}$ `Customer` relation to Node 2 over the network.
   * **Query Shipping:** Shipping the parameterized execution filter/sub-query directly to the data node, executing the join there, and returning only the matching tuples.
   * **Third-Party Integration:** If the query initiates at Node 3 (which holds neither table), the optimizer determines whether to ship both relations to Node 3 or execute an intermediate join between Nodes 1 and 2 and transfer the final output to Node 3.

### IV. The CAP Theorem

#### Overview & Theoretical Foundation
The CAP Theorem asserts that any distributed data store operating over an asynchronous, partitionable network can simultaneously provide at most two of the following three guarantees: **Consistency ($C$)**, **Availability ($A$)**, and **Partition Tolerance ($P$)**. 

```
                                  CAP Theorem
                             /-------------------\
                            /                     \
                           /   Partition Tolerance \
                          /            (P)          \
                         /                           \
                        /                             \
                       /   CP System       AP System   \
                      /   (HBase,         (Cassandra,   \
                     /     MongoDB,         Dynamo,      \
                    /      Redis)           CouchDB)      \
                   /                                       \
                  /-----------------------------------------\
                 /                                           \
    Consistency (C) <-------------------------------------> Availability (A)
                                   CA System
                             (Traditional RDBMS:
                           PostgreSQL, MySQL / Single)
```

In physical distributed clusters, network hardware faults, fiber cuts, and switch partitions are inevitable. Thus, **Partition Tolerance ($P$) is a mandatory operational requirement**. A distributed system cannot simply reject $P$; consequently, the real-world engineering trade-off simplifies to selecting between **Consistency ($CP$)** and **Availability ($AP$)** in the presence of a network partition.

#### Mechanics & Operational Invariants
Consider a three-node cluster ($A, B, C$) with data item $X = 49$, where a network partition isolates Node $C$ from Nodes $A$ and $B$. A client executes a write updating $X \leftarrow 50$ targeting Node $C$:

```
[Client] ---> Write (X = 50) ---> [Node C]   === PARTITION ===   [Node A] (X=49)   [Node B] (X=49)
```

Node $C$ faces mutually exclusive options:
1. **Selection 1: Prioritize Consistency over Availability ($CP$ Strategy):**
   * Node $C$ refuses to commit the write independently because it cannot reach $A$ and $B$ to coordinate synchronous updates.
   * Node $C$ either blocks the transaction waiting for network resolution (causing client timeout) or halts execution.
   * If a client times out without a deterministic response, **Availability is compromised**. However, **Consistency is preserved** because the system never surfaces conflicting values across nodes.
2. **Selection 2: Prioritize Availability over Consistency ($AP$ Strategy):**
   * Node $C$ accepts the write locally, updates $X \leftarrow 50$, and returns an immediate `SUCCESS` acknowledgment to the client.
   * **Availability is maintained** and the system remains **Partition Tolerant**.
   * However, another client reading from Node $A$ receives $X = 49$, while a client reading from Node $C$ receives $X = 50$. **Consistency is broken** in favor of continuous system uptime.
3. **Selection 3: Consistent & Available ($CA$ Strategy):**
   * Operates without network partitions ($P$). If a network partition occurs, the system fails to function as designed. This model characterizes traditional non-distributed relational systems (MySQL, PostgreSQL) deployed on reliable single-server nodes.

#### CAP Classification of Database Technologies
| Category | Primary Guarantee | Architectural Invariant | Representative Technologies |
| :--- | :--- | :--- | :--- |
| **CA** | Consistency + Availability | Disallows physical network partitions. Demands continuous full-cluster connectivity. | Traditional Relational Engines (PostgreSQL, MySQL, standard RDBMS) |
| **CP** | Consistency + Partition Tolerance | Blocks writes or returns operational errors under network splits to prevent stale reads. | HBase, MongoDB, Redis |
| **AP** | Availability + Partition Tolerance | Accepts writes locally during network partitions; permits temporary inconsistency. | Apache Cassandra, CouchDB, Amazon DynamoDB |

### V. ACID vs. BASE Architectural Paradigms

#### Overview & Theoretical Foundation
The structural tension between strict consistency and high availability manifests as two contrasting database design philosophies: **ACID** (Atomicity, Consistency, Isolation, Durability) and **BASE** (Basically Available, Soft State, Eventual Consistency). 

ACID governs relational architectures prioritizing data correctness above all else, enforcing pessimistic coordination mechanisms such as locks and distributed two-phase commits. In contrast, BASE emerged from modern web-scale and big data systems that cannot tolerate write blocking or coordination latency. BASE relaxes the requirement for instantaneous global consistency, guaranteeing that the cluster will reach consensus *eventually* once updates have propagated across all physical replicas.

#### Mechanics & Operational Invariants
1. **Core Components of BASE:**
   * **Basically Available (BA):** The system guarantees that incoming read or write requests always receive an explicit response (success or failure), even during partial server crashes or network outages. Availability is preserved by decoupling the user-facing request from backend replica synchronization.
   * **Soft State (S):** Data values may mutate without direct client intervention because the system allows asynchronous convergence. A node may temporarily return stale or divergent data while background gossip protocols propagate recent mutations.
   * **Eventual Consistency (E):** In the absence of new write operations, all replicas eventually sync and converge to the identical latest value over a finite window of time.
2. **Domain Fit & Use-Case Mapping:**
   * **ACID Requirements:** Essential for banking ledgers, financial debit/credit operations, and inventory reconciliation where an inconsistency of even 500 rupees directly corrupts business state.
   * **BASE Requirements:** Optimal for social media feeds (e.g., clicking a "Like" button or adding a post comment). If a like count takes 2–3 seconds to reflect across global timelines following a page refresh, the temporary inconsistency causes no system harm, while the absence of coordination delivers high horizontal scalability and microsecond response latencies.

#### Comparative System Analysis
| Evaluation Parameter | ACID Paradigm | BASE Paradigm |
| :--- | :--- | :--- |
| **Primary Design Objective** | Strict transaction correctness & data integrity | High availability & boundless horizontal scalability |
| **Consistency Guarantee** | **Strong Consistency:** Data is consistent immediately upon transaction commit | **Eventual Consistency:** Replicas diverge temporarily, converging over time |
| **Transactional Invariant** | Strict, pessimistic distributed transaction guarantees (e.g., 2PC) | Relaxed transactional rules; accepts localized updates |
| **Data State Boundary** | Deterministic; no uncommitted intermediate reads | **Soft State:** Replicas may serve stale data across synchronization windows |
| **Availability Impact** | Reduced under network splits or node stalls to preserve correctness | Maximum; nodes accept writes locally without synchronous network waits |
| **Cluster Scalability** | Bounded; cross-node coordination overhead scales unfavorably ($O(n)$) | Unbounded horizontal scale across commodity server clusters |
| **Canonical Workloads** | Financial accounting, payment processing, inventory reservation | Social activity feeds, recommendation engines, clickstream logging |
